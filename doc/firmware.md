# Фърмуер — бележки и решения

> Документът се допълва с напредването на софтуерната разработка.
> Принцип: **само необходимото** — минимум зависимости и включени модули.

## 1. RGB светодиод WS2812

Вграденият светодиод на ESP32-S3-Zero (GPIO21) изисква драйвер за протокола WS2812
(времена ~0.3 / 0.9 µs, период 1.25 µs) — обикновено управление на GPIO не е достатъчно.
Референтните библиотеки `esp-led-status` и `outputwrite/led_indicator` управляват обикновен светодиод
(GPIO / LEDC) и не поддържат WS2812.

### 1.1 Избор на драйвер

| Вариант | Плюсове | Минуси |
|---|---|---|
| **`espressif/led_strip` (RMT бекенд)** ← *избор* | официален и поддържан от Espressif; проверени времена; малко API | външна зависимост (един компонент, без допълнителни зависимости) |
| Директно RMT + собствен енкодер | нулеви зависимости | собствен код за поддръжка (~80 реда) — дублира `led_strip` |
| SPI бекенд на `led_strip` | — | заема SPI контролер; излишно за 1 светодиод |

Неизползваният код (напр. SPI бекендът на `led_strip`) се отстранява от линкера (`--gc-sections`),
така че в изпълнимия файл влиза само RMT частта.

### 1.2 Минимална конфигурация

`main/idf_component.yml`:

```yaml
dependencies:
  espressif/led_strip: "^3.0.0"
```

Инициализация (1 светодиод, RMT, без DMA):

```c
#include "led_strip.h"

static led_strip_handle_t s_led;

void status_led_init(void)
{
    const led_strip_config_t strip_cfg = {
        .strip_gpio_num = 21,                 // вграден WS2812 на ESP32-S3-Zero
        .max_leds = 1,
        .led_model = LED_MODEL_WS2812,
        .color_component_format = LED_STRIP_COLOR_COMPONENT_FMT_GRB,
    };
    const led_strip_rmt_config_t rmt_cfg = {
        .clk_src = RMT_CLK_SRC_DEFAULT,
        .resolution_hz = 10 * 1000 * 1000,    // 10 MHz → стъпка 0.1 µs
        .mem_block_symbols = 0,               // 0 = минималният размер по подразбиране
        .flags.with_dma = false,              // DMA е излишна за 1 светодиод
    };
    ESP_ERROR_CHECK(led_strip_new_rmt_device(&strip_cfg, &rmt_cfg, &s_led));
    led_strip_clear(s_led);                   // изгасен при старт
}
```

Принципи за минимална употреба:
- Обновяване (`led_strip_set_pixel` + `led_strip_refresh`) **само при промяна** на цвета/състоянието,
  не в постоянен цикъл.
- Шаблоните (мигане, дишане) — с един `esp_timer`, без отделна FreeRTOS задача.
- Яркостта — мащабиране на R/G/B в нашия слой (един коефициент), не в драйвера.

### 1.3 Яркост

- **Решение: 20 %** (коефициент 0.2 върху 0 – 255). Проверено на хардуера: при 25 % синьото вече е доста ярко.
- При нужда се коригира в Kconfig (`CONFIG_SH_LED_BRIGHTNESS`) след монтаж в кутията.
- Предвижда се като настройка (константа / Kconfig, по-късно евентуално и в NVS).

### 1.4 Логика на индикацията

Цветове, шаблони и приоритети: [led-indication.md](led-indication.md). Реализация (стъпка 5):

- `sh_ind` (чист C, тест на компютъра) — една функция `sh_ind_update()`: активните кодове, помпата, колекторът,
  ваканцията (засега винаги изключена), Wi-Fi → (цвят, шаблон). Извиква се от `sh_control` само при промяна на
  входовете.
- Цвят по приоритет: червен (`E1`, `E2`, `E4`, `E5`, `E6`) → оранжев (`Hot`, `Fro`) → лилав (ваканция) → жълт
  (колектор > 90 °C, помпата спряна; отпада под 88 °C) → зелен (помпата работи — и тестът, защитата от блокиране,
  режимите при повреден датчик) → бял (колектор < 20 °C; отпада над 22 °C) → син. Праговете —
  `CONFIG_SH_LED_COLD_C` (20) и `CONFIG_SH_LED_HOT_C` (90), зоната на връщане 2 K. Без валидна стойност на
  колектора (преди първата или повреден датчик) — нито бял, нито жълт.
- Шаблон: червен — бързо 150 / 150 ms (`E4`, `E5`, и при аварии от двете групи) или двойно (100 вкл., 100 изкл.,
  100 вкл., 1000 тъмно: `E1`, `E2`, `E6`); останалите цветове — постоянно при връзка с Wi-Fi, проблясък 80 ms на
  всеки 2 s без връзка или докато е отворен порталът.
- `sh_led` — един периодичен `esp_timer` на 10 ms (всички времена са кратни на 10 ms): изчислява дали светодиодът
  свети в момента на шаблона и пише в него **само при промяна**; само таймерът пише в светодиода. Нов шаблон
  започва отначало, нов цвят продължава текущия шаблон. Оранжевият цвят: R 255, G 60, B 0 (преди яркостта) — за
  проверка на хардуера.

### 1.5 Ресурси (RMT)

ESP32-S3 има 4 TX и 4 RX RMT канала. Светодиодът заема **1 TX канал**. DS18B20 не ползват RMT: собственият
драйвер `ds18b20` управлява 1-Wire програмно (прекъсванията са спрени само за един слот, ≤ 70 µs).
Компонентите на Espressif `onewire_bus` + `ds18b20` (RMT) бяха разгледани и отхвърлени: само ESP-IDF 5.x,
без ESP8266, по 1 TX + 1 RX канал на шина.

## 3. HomeKit — прозорец за сдвояване

Проверено в [esp-homekit-sdk](https://github.com/espressif/esp-homekit-sdk) (`components/homekit/esp_hap_core`):

| Елемент | Стойност / API | Бележка |
|---|---|---|
| Продължителност на прозореца | `HAP_PAIRING_MODE_TIMEOUT_IN_MINS = 10` (`src/esp_hap_pair_setup.c`) | по HAP Spec R16; вътрешен таймер `hap_pairing_mode_timer` |
| Таймерът се стартира | при старт без сдвоени контролери; при премахване на последния контролер; при всяко Pair Setup M1 (рестарт); при `hap_pair_setup_re_enable()` | вътрешни извиквания на `hap_start_pairing_mode_timer()` |
| Край на прозореца (изтекло време) | събитие `HAP_EVENT_PAIRING_MODE_TIMED_OUT` | SDK-то спира mDNS обявяването — аксесоарът вече не се вижда за сдвояване |
| Успешно сдвояване | събитие `HAP_EVENT_CTRL_PAIRED` | |
| Опит за сдвояване | `HAP_EVENT_PAIRING_STARTED` / `HAP_EVENT_PAIRING_ABORTED` | |
| Премахнат контролер | `HAP_EVENT_CTRL_UNPAIRED` (+ проверка `hap_get_paired_controller_count() == 0`) | прозорецът се отваря отново |
| Ново отваряне на прозореца | `hap_pair_setup_re_enable()` (публична функция в `hap.h`) | напр. от бутон, без рестарт |
| Брой сдвоени контролери | `hap_get_paired_controller_count()` | |

Няма публична функция „отворен ли е прозорецът“ — състоянието се поддържа във фърмуера от горните събития:

```c
static bool s_pair_window_open;

static void hap_event_handler(hap_event_t event, void *data)
{
    switch (event) {
    case HAP_EVENT_CTRL_PAIRED:
    case HAP_EVENT_PAIRING_MODE_TIMED_OUT:
        s_pair_window_open = false;           // спира дишането
        break;
    case HAP_EVENT_CTRL_UNPAIRED:
        if (hap_get_paired_controller_count() == 0) {
            s_pair_window_open = true;        // SDK-то стартира нов прозорец
        }
        break;
    default:
        break;
    }
    // → преизчисляване на индикацията и енергийния режим
}
// След hap_start(): s_pair_window_open = (hap_get_paired_controller_count() == 0);
// При hap_pair_setup_re_enable():  s_pair_window_open = true;
```

## 4. Енергиен режим на Wi-Fi

- Wi-Fi **не се изключва** — няма отделен режим за настройка с изключване на радиото.
- **Намалена мощност** се прилага само в един случай: прозорецът за сдвояване с HomeKit е изтекъл
  (`HAP_EVENT_PAIRING_MODE_TIMED_OUT`), **без да е имало опит за сдвояване** (не е получено `HAP_EVENT_PAIRING_STARTED`)
  и аксесоарът е останал несдвоен.
  - Мярка: по-ниска максимална мощност на предавателя — `esp_wifi_set_max_tx_power()` (стойността се уточнява на място;
    напр. от ~20 dBm към ~11 – 13 dBm).
  - Нормалната мощност се възстановява при ново отваряне на прозореца (`hap_pair_setup_re_enable()`) и при сдвояване.
- Ако устройството вече е било свързано и **връзката с Wi-Fi се загуби** — енергийният режим на чипа **не се променя**
  (само индикацията преминава в проблясък, а Wi-Fi стекът сам опитва повторно свързване).

## 5. Локално управление — дисплей и бутони

- Бутони: 3 × GPIO с библиотеката `button` (кратко/дълго натискане, автоматично повторение).
- Обновяване на дисплея само при промяна на показваната стойност.
- Дисплей: TM1637, 3 цифри — библиотека [esp_tm1637](https://github.com/AramVartanyan/esp_tm1637); клавиатурата на TM1637 не се използва.

### 5.1 Обновяване на `esp_tm1637` — договорени промени

> Статус: **реализирано в `esp_tm1637` 1.1.0** (компилира се за ESP32, -S3, -C3; тест на хардуер предстои).

| # | Проблем | Решение |
|---|---|---|
| 1 | Изборът на платформа е по `CONFIG_IDF_TARGET_ESP32` / `ESP8266` — за ESP32-S3 (и всички други чипове) се избира клонът за esp-open-rtos и **не се компилира** | Проверка за **`ESP_PLATFORM`** — дефинира се от системата за изграждане на ESP-IDF (и ESP8266_RTOS_SDK) за всички чипове; esp-open-rtos — само ако не е дефиниран |
| 2 | API, премахнато/преместено в ESP-IDF 5.x (`GPIO_PIN_INTR_DISABLE`, `esp32/rom/ets_sys.h` / `ets_delay_us`) | Условия по версия чрез `esp_idf_version.h`: `ESP_IDF_VERSION >= ESP_IDF_VERSION_VAL(5, 0, 0)` → `esp_rom_sys.h` / `esp_rom_delay_us()`, `GPIO_INTR_DISABLE`; за ESP-IDF 4.x и ESP8266 — досегашните извиквания (точната граница на версиите се проверява при реализацията) |
| 3 | Безкрайно изчакване на ACK — при липсващ/повреден дисплей фърмуерът увисва | Изчакване с **ограничение** (напр. до ~100 µs на стъпки от 1 µs); при таймаут — освобождаване на шината (стоп), връщане на грешка и флаг „дисплеят не отговаря“; следващ опит след определено време (напр. 5 s), за да не се губи време при всяко обновяване |
| 4 | Само 4 или 6 цифри | Обща поддръжка за **1 – 6 цифри** (практически 3 и 4); функциите за температура/число — съобразени с броя цифри |
| 5 | CLK/DIO са push-pull изходи, DIO се превключва изход ↔ вход | **Open-drain** режим (`GPIO_MODE_INPUT_OUTPUT_OD`) — виж обяснението по-долу |
| 6 | `malloc` без проверка; няма освобождаване; няма защита при няколко задачи | Проверка за `NULL` (връща `NULL` при неуспех); функция `tm1637_delete()`; правило: дисплеят се обслужва **само от една задача** (без mutex — без допълнителни ресурси) |
| 7 | Клавиатурата на TM1637 не се поддържа | Не е нужна — бутоните са на GPIO |

**Защо open-drain (т. 5):**
- Сега ESP32 *активно* подава и „0“, и „1“ на DIO (push-pull). След 8-ия бит TM1637 дърпа DIO към GND за ACK.
  Ако последният изпратен бит е „1“, за кратко (докато библиотеката превключи DIO на вход) ESP32 подава „1“,
  а TM1637 — „0“: двата изхода се „борят“ (кратко съединение през изходните транзистори).
- При open-drain ESP32 само дърпа линията към GND или я **пуска**; „1“ се осигурява от pull-up резистора (към 3.3 V).
  Така двете страни никога не могат да се борят, няма нужда от превключване изход/вход
  (ESP32 чете нивото на същия извод), а логиката е същата като при I2C.
- Изисква външни pull-up резистори (10 kΩ към 3.3 V — вече предвидени на платката);
  вътрешните (~45 kΩ) са твърде слаби за чисти фронтове.

### Нормален режим на дисплея

Циклично, докато не се влезе в менюто или не тръгне тестът на помпата:

| Стъпка | Показва | Време |
|---|---|---|
| 1 | надпис `Boil` (бойлер) | 1 s |
| 2 | температурата на бойлера | 5 s |
| 3 | надпис `Col` (колектор) | 1 s |
| 4 | температурата на колектора | 5 s |

- „Boil“ на 3 цифри: `b`, `o`, а „i“ (сегмент E) и „l“ (сегменти B, C) са в една цифра. „Col“: `C`, `o`, `l`
  (сегменти E, F). Надписите са зададени като сегменти (XGFEDCBA) в `sh_display.c`.
- Температура: `23.2`, `-9.9`, `150`, `-12` (3 цифри); при неуспешно измерване — последната валидна стойност;
  `---` при **повреден** датчик (5 поредни неуспешни измервания) или преди първата валидна стойност.
- Нова стойност по време на 5-те секунди се показва веднага (проверка на 50 ms); дисплеят се пише само при
  промяна на показаното.
- След стъпка 4 — активните кодове (виж „Аварии и информация“), по 1 s, после цикълът отначало.
- При всяко връщане в нормалния екран (от менюто, след теста) цикълът започва от `Boil`.
- Дисплеят се управлява само от задача `sh_display` (`esp_tm1637`: една задача на дисплей); задачата на
  управлението само записва температурите в общото състояние, а менюто (в задачата на бутоните) — какво се
  показва от него (`sh_buttons_menu_view()`).

### Потребителско меню

Позиции в този ред: `tbo`, `C.Lo`, `d.on`, `d.oF`, `tSt`, `End` (`SSn`, `HoL`, `nEt` — в стъпките на своите
функции). Стойностите са цели числа, подравнени вдясно.

| Име | Параметър | Обхват | Стъпка | По подразбиране (Kconfig „Control“) |
|---|---|---|---|---|
| `tbo` | Tmax на бойлера | 30 – 85 °C | 1 | `SH_TANK_MAX_C` (70) |
| `C.Lo` | Минимална температура на колектора | 10 – 80 °C | 1 | `SH_COL_MIN_C` (25) |
| `d.on` | Разлика за включване | 3 – 20 K, ≥ `d.oF` + 1 | 1 | `SH_DIFF_ON_K` (6) |
| `d.oF` | Разлика за изключване | 1 – 15 K, ≤ `d.on` − 1 | 1 | `SH_DIFF_OFF_K` (4) |
| `tSt` | Време за тест на помпата | 60 – 900 s | 30 s | `SH_PUMP_TEST_S` (300) |

| Къде | „+“ / „−“ | Кратко „меню“ |
|---|---|---|
| Нормален екран | „+“ — тест на помпата; „−“ — нищо (по време на теста: ± 60 s) | влиза в списъка, на `tbo` (по време на теста: спира теста) |
| Списък | следваща / предишна позиция, в кръг (след `End` → `tbo`) | на параметър — стойността мига (0.5 s / 0.5 s); на `End` — нормалният екран |
| Стойност (мига) | ± една стъпка в обхвата, без превъртане; задържане > 1 s → повторение на 200 ms | потвърждава: записва само ако е различна; стойността стои неподвижна 1 s, после списъкът на същата позиция |

- **10 s без натискане** в списъка или на стойност → нормалният екран; непотвърдена стойност не се записва.
- Докато стойността стои неподвижна след потвърждението (1 s), натисканията не се вземат предвид.
- След промяна на стойността миганието започва отначало (новата стойност се вижда веднага).
- Задържане на „+“ / „−“ (повторение) действа само на стойността; в списъка и в нормалния екран задържане над
  1 s не прави нищо (кратко натискане, пуснато след повторение, не се брои — библиотеката `button` подава
  „tap“ и тогава).
- В менюто грешките не се показват. Задържането на „меню“ за нулиранията работи навсякъде (и в менюто).
- Логиката на преходите — `sh_menu` (чист C, тест на компютъра); натисканията идват от `sh_buttons`.

**Запис (`sh_settings_store`):** дял `nvs`, пространство на имената `sh_settings`, ключове `tbo`, `c_lo`,
`d_on`, `d_of`, `t_st` (int16). Четат се при старта; липсваща, извън обхвата или извън стъпката стойност → по
подразбиране; записана двойка с `d.oF` ≥ `d.on` → и двете по подразбиране. Запис само при промяна. Фабричното
нулиране изтрива `nvs` → стойностите по подразбиране. Управлението чете настройките на всеки цикъл (1 s) —
промяната важи веднага. Минималните времена, защитата на колектора и периодът на измерване остават в Kconfig
(сервизни настройки — по-късно в уеб интерфейса).

### Тест на помпата

- Кратко „+“ в нормалния екран → помпата тръгва **веднага** (без минимален престой) за `tSt`.
- Спират я / не я пускат само забраната при горещ колектор и аварийният таван на бойлера (защита, чийто
  датчик е повреден, не може да се провери); тестът работи и при повреден датчик. Такава граница **прекратява**
  теста (той не се възобновява, когато тя се отмени); „+“, докато тя е активна, не пуска тест (в лога
  `pump test started` и веднага `pump test ended`).
- „+“ → +60 s (остатъкът най-много 900 s); „−“ → −60 s, само ако остатъкът е над 60 s; „меню“ → край, но не
  по-рано от 1 min след пускането (заявката се изпълнява в края на първата минута).
- Дисплей: `tSt` 3 s, после оставащите секунди; `tSt` отново 1 s на всеки 7 s (6 s време, 1 s `tSt`).
- Край (изтекло време или „меню“): управлението продължава като от спряна помпа с изтекъл минимален престой —
  помпата остава включена, ако режимът би я пуснал (разликата, защитата на колектора, режимите при повреден
  датчик); иначе спира и престоят се брои от края. Минималното време на работа на продължилата помпа също се
  брои от края на теста.
- Тестът прекратява текуща защита от блокиране и текуща проба при повреден датчик.

### Защита от блокиране

- Константи: след **24 h** без работа на помпата (по каквато и да е причина; след рестарт — от старта) помпата
  се завърта за **60 s**, щом колекторът е поне колкото бойлера; ако това не стане до още **12 h** (36 h общо) —
  независимо от температурите. Тестът на помпата се брои за работа.
- Спират я (и я прекратяват) / не я пускат само забраната при горещ колектор и аварийният таван. Краят — както
  края на теста.
- При повреден датчик сравнението колектор ≥ бойлер не може да се направи → само правилото за 36 h; при двата
  повредени помпата остава спряна (само тестът е разрешен).

### Повреден датчик

**Измерване (`sh_sensors` + `sh_meas`):** неуспешно четене — няма отговор, грешна контролна сума, стойност
извън −55 … +125 °C, скок над 20 K спрямо последната валидна стойност → веднага втори опит с ново измерване;
при скок вторият опит се приема, ако е в рамките на 1 K от скока. Неуспешно измерване → последната валидна
стойност, брояч +1; **5 поредни** → датчикът е повреден (`sh_state`: `col_fault` / `tank_fault`, лог
`... sensor FAULTY`); успешно измерване → брояч 0, повредата отпада (лог `... sensor OK again`).

**Помпата (`sh_pump_ctl`):**

| Повреда | Поведение |
|---|---|
| двата датчика | помпата спряна (тестът — разрешен) |
| бойлер | пускане при колектор ≥ 60 °C (минималният престой важи), спиране под 58 °C (след минималното време); спиране веднага при колектор ≥ 95 °C, ново пускане под 93 °C; Tmax и таванът на бойлера не се ползват; забраната при горещ колектор важи. **Проба:** при спряна помпа и колектор ≥ прага на защитата на колектора (110 °C, таван 115 °C) — работа за минималното време (без престой); в края колекторът < 93 °C → зареждането продължава; иначе спиране и следваща проба не по-рано от 5 h (и след спиране от забраната при горещ колектор по време на пробата) |
| колектор | проба 10 min; покачване на бойлера ≥ 0.5 K → продължава с проверка на всеки 10 min; без покачване → спиране; изчакване 30 / 60 / 120 min след 1 / 2 / ≥ 3 поредни неуспешни проби, след работа с покачване — 30 min; първата проба — веднага щом датчикът е обявен за повреден (минималният престой важи); бойлер ≥ 95 °C (от помпата или от нагревателя) → спиране веднага и проба не по-рано от 5 h; Tmax не се ползва; **нагревател:** покачване ≥ 0.5 K за последните 10 min при спряна помпа (проба на бойлера всяка минута) → пробата се отлага |
| възстановяване | нормалната логика продължава с текущото състояние на помпата и времето от последното превключване |

Без валидна стойност от старта, докато датчикът не е обявен за повреден → помпата спряна (`sensor fault`).

### Аварии и информация

`sh_alarm` (чист C, тест на компютъра) — на всеки цикъл на управлението (1 s), след решението за помпата:

| Код | Активен, докато |
|---|---|
| `E1` | датчикът на колектора е повреден |
| `E2` | датчикът на бойлера е повреден |
| `E4` | границата на аварийния таван на бойлера е активна (≥ 95 °C, отпада под 93 °C) и датчикът на бойлера не е повреден |
| `E5` | забраната при горещ колектор е активна (≥ изчислената точка на кипене, отпада под нея − 2 K) и датчикът на колектора не е повреден |
| `E6` | повреда на помпата / няма поток — по-долу |
| `Hot` | помпата работи по защитата на колектора или по пробата при аварийна температура при повреден бойлер (информация) |
| `Fro` | помпата работи по защитата от замръзване (информация; стъпка 6) |

`E4` и `E5` ползват границите на `sh_pump_ctl` (същите, които спират помпата).

**`E6`** ([led-indication.md](led-indication.md), т. 6): проверява се само докато помпата работи непрекъснато по
нормалното управление (разлика, минимално време на работа, защита на колектора) и без повреден датчик. Първите
10 min от пускането се пропускат; от 10-ата минута — проба на двете температури всяка минута, а от 20-ата
минута, всяка минута — сравнение с пробата отпреди 10 min (плъзгащ прозорец, изцяло след първите 10 min):
- **обявяване:** колекторът нараснал ≥ 10 K, бойлерът < 0.5 K и разликата колектор − бойлер ≥ 20 K;
- **отпадане** (при същите проверки): бойлерът нараснал ≥ 0.5 K или разликата под 10 K;
- иначе `E6` стои — и при спряна помпа, тест, защита от блокиране, повреден датчик — до следваща проверка или
  рестарт. Спиране или смяна на причината с ненормална прекъсва работата: при следващото пускане 10 min отначало.
- Праговете — Kconfig „Control“: `SH_E6_TIME_MIN` (10 min — пропуснатото време и прозорецът, 5 – 30),
  `SH_E6_COL_RISE_K` (10), `SH_E6_TANK_RISE_DK` (5 = 0.5 K), `SH_E6_DIFF_K` (20), `SH_E6_CLEAR_DIFF_K` (10;
  проверка при компилиране: под `SH_E6_DIFF_K`). Логиката на помпата не се променя.

Активните кодове се публикуват в `sh_state` (`alarms`, бит на код); всяка поява и отпадане — ред в лога
(`W sh_control: E6 active: collector 75.0 °C, tank 40.0 °C`, `... E6 cleared: ...`).

**Дисплей:** след стандартния цикъл — активните кодове по 1 s, първо авариите по номер, после `Hot`, после
`Fro`; после цикълът отначало. `E1` … `E6` подравнени вдясно (` E1`), `Hot` и `Fro` — на трите цифри. В менюто и на екрана на теста —
без кодове. **Светодиод:** виж т. 1.4.

### Данни на монтажника и изчислени граници (стъпка 6)

`sh_installer` (чист C, тест на компютъра) + `sh_installer_store` (дял `nvs`, пространство на имената
`sh_installer`, ключове `fluid`, `glycol`, `press`, `col_max`, int16):

| Данни | Обхват | По подразбиране (Kconfig „Installer data“) |
|---|---|---|
| Топлоносител | вода / пропилен-гликол | `SH_INST_GLYCOL` (изкл. = вода) |
| Пропилен-гликол | 0 – 60 %, стъпка 1 %; при вода — 0 | `SH_INST_GLYCOL_PCT` (0) |
| Минимално налягане (манометър, студена система) | 0.5 – 6.0 bar, стъпка 0.1 (пази се в десети) | `SH_INST_PRESSURE_DBAR` (15 = 1.5 bar) |
| Максимална температура на колектора | 100 – 250 °C, стъпка 1 | `SH_INST_COL_MAX_C` (120) |

- Липсваща или извън обхвата стойност → по подразбиране; гликол при вода → 0. Запис само при промяна. Променят се
  от раздела „Сервизни“ на уеб интерфейса (с кода).
- **Точка на кипене:** вода при абсолютно налягане = манометъра + 1.013 bar по уравнението на Антоан (mmHg, °C;
  A = 8.14019, B = 1810.94, C = 244.485; 1 bar = 750.062 mmHg) + добавка от гликола 0 / 20 / 30 / 40 / 50 / 60 % →
  0 / 1 / 2 / 3 / 4 / 6 K (линейно между точките), закръглена **надолу** до 0.1 °C. Вода, 1.5 bar → 127.7 °C;
  9 % PG, 2.2 bar → 136.5 °C.
- **Таван на защитата на колектора** = min(макс. температура на колектора − 5 K, точката на кипене − 10 K);
  настройката `SH_COL_PROTECT_C` (110 °C) се ограничава до него. **Забрана за пускане** = точката на кипене
  (отпада под нея − 2 K).
- **Праг на защитата от замръзване:** вода → 4 °C; пропилен-гликол → точката на замръзване на сместа
  (0 / 10 / … / 60 % → 0 / −3 / −8 / −14 / −22 / −33 / −48 °C, линейно между точките) + 4 K, в границите −40 … +10 °C.
- Константите `SH_PUMP_COL_BOILING` и `SH_PUMP_COL_PROTECT_CAP` са заменени с полета в параметрите на помпата
  (`col_boiling`, `col_protect_cap`); `sh_control` ги взима на всеки цикъл — промяна на данните важи веднага, без
  рестарт. В лога при старта и при всяка промяна: `boiling point (no start) 127.7 °C, collector protection ceiling
  115.0 °C, frost threshold 4.0 °C` и, ако настройката е над тавана, `W … collector protection 110 °C is limited
  to 101.6 °C`.

### Защита от замръзване (стъпка 6)

- В `sh_pump_logic` (нормалният режим), с приоритет: забраната при горещ колектор → аварийният таван → защитата
  на колектора → **защитата от замръзване** → Tmax → разликата. Тестът и защитата от блокиране — както досега.
- **Пускане:** колекторът под прага и бойлерът ≥ 5 °C → веднага (без минимален престой). **Спиране:** колекторът
  ≥ прага + 2 K след минималното време на работа; бойлерът под 5 °C (или изключена защита) → веднага — тогава
  следващите правила решават като за спряна помпа.
- При повреден датчик (режимите на `sh_pump_ctl`) не се проверява.
- Включена / изключена — превключвател в „Настройки“ на уеб интерфейса; пази се в `sh_settings` (ключ `fro`,
  по подразбиране `SH_FROST_PROTECT` = включена).
- Причина `frost protection`; код `Fro` (информация), докато помпата работи по нея; светодиодът — оранжев.

### Часовник (стъпка 9)

Логика и решения: [operating-modes.md](operating-modes.md), т. 3.1. Реализация:

- `sh_clock_sync` — системният часовник (UTC) и часовата зона. **SNTP** (`pool.ntp.org`, `esp_sntp`): пуска се при
  първото свързване с рутера, при всяко следващо свързване пита веднага (`sntp_restart()`), после на всеки **12 h**.
  **Часът от браузъра** (`POST /api/time`, при всяко отваряне на страницата, без кода) се приема само ако
  часовникът не е сверен по SNTP през последните 24 h (`sh_clock_browser_ok()`); браузър с час преди 2024 г. се
  отхвърля. След старта часовникът е **несверен** до първото от двете (и след рестарт без спиране на тока).
- **Часова зона:** списък от 78 зони в `sh_clock.c` (име по IANA → правило POSIX `TZ` с лятното часово време);
  страницата го взима от `GET /api/zones`. Избраната зона се пази по име в дял `nvs` (пространство `sh_clock`,
  ключ `tz`) и се прилага веднага (`setenv("TZ")` + `tzset()`). Без запазена зона — **непотвърдена**, местното
  време е UTC. Страницата предлага зоната на браузъра (бутон „Задай …“ в „Система“); записът е с кода
  (`POST /api/set`, `tz=<номер в списъка>`). Зона, която липсва в списъка — най-близката със същото правило.
- **Проверка по пика на колектора** (`sh_clock`: `sh_peak_day()`, чист C) — в полунощ, за всеки **цял** ден
  (наблюдаван от полунощ до полунощ със сверен часовник): слънчев, ако максимумът на колектора е ≥ 20 K над
  минимума му за деня; пикът — минутата на максимума (първото достигане); в норма 10:00 – 17:00 включително.
  2 поредни слънчеви дни извън → **ненадежден**; 2 поредни вътре → отново надежден; облачните и непълните дни не
  се броят и не прекъсват поредицата. Състоянието е в RAM.
- **Надежден часовник** = сверен и проверката не го отрича. Нов часовник (първо сверяване, скок над 1 h или през
  ден), нова зона и нулирането на научените стойности започват проверката отначало: с **потвърдена зона** —
  надежден веднага; с непотвърдена (UTC по подразбиране) — ненадежден до 2 поредни слънчеви дни с пик в прозореца.
- Публикува се в `sh_state` (`clock_set`, `clock_reliable`) от `sh_control`; местното време — `sh_clock_now()`
  (ден от 2020 г., секунди от полунощ, зона). Логиката, която го ползва — групи C и D.
- Лог: `clock set by SNTP`, `clock set by the browser`, `time zone Europe/Sofia`, `time zone check: the clock is
  NOT reliable`.

### История (стъпка 9)

Формат и решения: [web-interface.md](web-interface.md), т. 4 и 4.1. `sh_history` (чист C) + `sh_history_store`
(дялът, mutex); `sh_control` подава стъпка всяка секунда.

- **Графика за деня (RAM, 144 интервала):** интервалът свършва на 10-минутните марки на местното време (без
  часовник — на 10 min от старта); пази температурите в края му (без стойност при повреден датчик) и секундите
  работа на помпата по вид. Със сверен часовник графиката показва интервалите след полунощ, без часовник —
  последните 24 h. Часовник, сверен по-късно (напр. от браузъра): измереното преди това остава, с изчислено
  местно време.
- **Вид на работата на помпата:** зареждане — разликата, минималното време на работа, зареждането при повреден
  датчик (`tf_run`, `cf_run`); защита — защитата на колектора, замръзването и пробата при аварийна температура
  на колектора с повреден датчик на бойлера (`tf_probe`, кодът `Hot`); друго — тест, защита от блокиране, проба
  при повреден датчик на колектора.
- **„Работа днес“:** сборът от секундите за деня (без часовник — за последните 24 h).
- **Дневно обобщение:** в полунощ местно време, само при сверен часовник — запис от 32 B (little-endian):

  | Байт | | |
  |---|---|---|
  | 0 | u16 | дата — ден от 01.01.2020 (местна) |
  | 2 | 4 × i16 | макс. / мин. на колектора, макс. / мин. на бойлера, 0.1 °C (−1000 = няма стойност) |
  | 10 | 3 × u16 | минути работа на помпата: зареждане / защита / друго |
  | 16 | u16, u16 | минути нощно охлаждане, минути на нагревателя (0 до групи C / D) |
  | 20 | u16 | кодове през деня — битове по реда `E1`, `E2`, `E4`, `E5`, `E6`, `Hot`, `Fro` |
  | 22 | u16 | битове 0 – 10: минутата на пика на колектора (0x7FF = няма); бит 14: денят не е цял; бит 15: часовникът е надежден |
  | 24 | u16, u16, u8 | научени: изгрев, залез (минути от полунощ; 0xFFFF = няма данни), цел на охлаждането (°C; 0xFF = няма данни) |
  | 29 | u8 | версия (1) |
  | 30 | u8 | резерв (0) |
  | 31 | u8 | CRC-8 (полином 0x07, начало 0xFF) на байтове 0 – 30 |

  Ден, започнал след полунощ (рестарт, късно сверен часовник), се записва като **непълен** и не участва в
  проверката на зоната. При нов часовник (скок) старият ден не се записва.
- **Дял `history`** (`data`, подтип `0x40`, `0x350000`, 64 KB = 16 сектора × 128 записа): кръгов буфер — записите
  се редят един след друг; преди да се запише последният свободен запис, се изтрива следващият сектор (най-старите
  128 дни). Така винаги има поне един празен запис и мястото на най-новия се намира след всяко спиране на тока
  (най-дългата поредица празни записи). Пазят се 1920 – 2047 дни; сектор се изтрива веднъж на 128 дни. Повреден
  запис (контролна сума, версия) се пропуска; прекъснато изтриване на сектор се повтаря при старта; съдържание,
  което не е дневник (няма празен запис), се изтрива. Записът се проверява с четене.
- **Без дела** (обновяване по OTA със старата таблица) — в лога `no "history" partition …`; дневните обобщения са
  изключени, функцията `history` липсва в списъка (в уеб интерфейса е сива), всичко останало работи.
- **CSV** (`GET /api/history.csv`, изпраща се на части по 1 KB): всички записи от най-стария; разделител `;`,
  десетична точка, край на реда CRLF; заглавен ред `date;col_max;col_min;tank_max;tank_min;pump_charge_min;`
  `pump_protect_min;pump_other_min;cooling_min;heater_min;codes;col_peak;clock_reliable;whole_day;sunrise;sunset;`
  `cool_target`; празно поле = няма данни; кодовете — с интервал (`E1 Hot`).
- Лог в полунощ: `2026-11-11 ended: collector -1.8 ... 118.7 degC, peak at 13:10`.

**Уеб интерфейс — добавено в стъпка 9:**

| Адрес | |
|---|---|
| `GET /api/state` | добавени: `run` (секунди работа днес по вид), `clock` (`set`, `ok`, `min` — минута от деня), `tz` (номер на зоната, −1 = непотвърдена), `peak` (`min`, `in`; `null` — още няма слънчев ден); `feat` съдържа `history` само при наличен дял |
| `GET /api/history` | графиката (`day`: 1 — от полунощ, 0 — последните 24 h; `pts`: `[x, колектор, бойлер, s зареждане, s защита, s друго]`, x — минута от деня / минути назад) и последните 7 дни (`days`) |
| `GET /api/history.csv` | всички дневни обобщения |
| `GET /api/zones` | имената на часовите зони |
| `POST /api/time` | `t=<секунди от 1970, UTC>` — часът на браузъра, без кода |
| `POST /api/set` | добавено: `tz` — с кода |
| `POST /api/reset` | добавени: `what=learned` (проверката на зоната започва отначало), `what=history` (изтрива дяла) — с кода |

Заместителят на страницата (`make … sim`): часовникът е на компютъра; денят дотук и 10 дневни обобщения са
измислени при старта; `/sim?clock=0` — несверен часовник (следващото отваряне на страницата го сверява),
`/sim?hist=0` — без дял `history`.

### Нулиране с бутона „меню“

| Действие | Време (Kconfig) | Какво се изтрива | Кога става |
|---|---|---|---|
| Нулиране на Wi-Fi | ≥ 5 s, до фабричното (`CONFIG_SH_NET_RESET_HOLD_S`, 3 – 7 s) | само запазената мрежа (`captive_wifi_clear_credentials()` → `esp_wifi_restore()`) | при **пускане** на бутона |
| Фабрично нулиране | 9 s (`CONFIG_SH_FACTORY_RESET_HOLD_S`, 8 – 12 s) | **всичко** в дял `nvs`: сдвояванията с HomeKit, настройките на устройството, Wi-Fi мрежата | още докато бутонът е **задържан** |

- Двата диапазона не се застъпват; компилацията спира, ако фабричното време не е по-дълго.
- След нулирането устройството се рестартира и тръгва в портала `SOLAR-XXXXXX`.
- Фабричното нулиране спира Wi-Fi и изтрива целия дял `nvs` — същото, което прави `hap_reset_to_factory()`
  в esp-homekit-sdk (`hap_keystore_erase_all_data()`). Дялът `factory_nvs` (кодът за сдвояване) е само за четене
  и остава. При добавянето на HomeKit извикването се заменя с `hap_reset_to_factory()` (затваря и сесиите,
  спира mDNS обявяването). Затова всички настройки на устройството се пазят в дял `nvs`.
- Мрежата се пази от Wi-Fi драйвера (`captive-wifi` след 0.2.2: `WIFI_STORAGE_FLASH`, както `app_wifi` и
  `wifi_provisioning` на Espressif). Затова HomeKit вижда същата мрежа (`hap_wifi_is_provisioned()` чете
  `esp_wifi_get_config()`), а `hap_reset_network()` (`esp_wifi_restore()`) я изтрива — с HomeKit нулирането
  на Wi-Fi може да вика `hap_reset_network()` (затваря сесиите, спира mDNS, рестартира).
- HomeKit се стартира при първото свързване (както в mppt-1k): порталът вече е затворен, така уеб сървърът
  на портала и този на HomeKit (порт 80) никога не работят едновременно.
- Логът показва кога е достигнато времето за Wi-Fi („release now …“). Светлинна индикация — с шаблоните на светодиода.

## 6. Макет за разработка — вътрешни pull-up резистори

Докато хардуерът не е завършен, софтуерът се разработва върху **макет** (без окончателните платки).
За макета във фърмуера се **включват вътрешните pull-up резистори** на ESP32-S3 (~45 kΩ към 3.3 V):

| Линия | GPIO | Вътрешен pull-up | Как |
|---|---|---|---|
| DS18B20 колектор | GP1 | ✔ | `ds18b20`: `CONFIG_ONEWIRE_INTERNAL_PULLUP` (избира се от `CONFIG_SH_INTERNAL_PULLUPS`) |
| DS18B20 бойлер | GP2 | ✔ | `ds18b20`: `CONFIG_ONEWIRE_INTERNAL_PULLUP` (избира се от `CONFIG_SH_INTERNAL_PULLUPS`) |
| TM1637 CLK | GP5 | ✔ | `gpio_config()` — `pull_up_en = GPIO_PULLUP_ENABLE` |
| TM1637 DIO | GP6 | ✔ | `gpio_config()` — `pull_up_en = GPIO_PULLUP_ENABLE` |
| Бутони | GP7 – GP9 | ✔ (и в окончателния вариант) | библиотеката `button` |

- Настройка в Kconfig (напр. `CONFIG_SH_INTERNAL_PULLUPS`, по подразбиране **включена**), за да може след монтиране
  на външните резистори вътрешните да се изключат без промяна на кода.
- Вътрешните резистори са слаби (~45 kΩ) — по-бавни фронтове:
  - **DS18B20:** с кратки кабели обикновено работи; с дългите сонди (95 cm) е възможно нестабилно четене
    (грешки в CRC, „липсващ“ датчик). Ако се случи — един външен 4.7 kΩ на макета решава проблема.
  - **TM1637:** закъснението в библиотеката (сега 3 µs) да е настройваемо, за да може при нужда да се увеличи
    (напр. 10 – 20 µs) — за дисплея скоростта не е важна.
- ⚠️ Ако на макета се ползва **готов модул с TM1637**, той често има собствени pull-up резистори към своето VCC.
  При модул, захранен от 5 V, те трябва да се свалят/преместят към 3.3 V и на макета.
- В окончателните платки остават външните резистори: 4.7 kΩ за датчиците и 10 kΩ за TM1637, към 3.3 V.
