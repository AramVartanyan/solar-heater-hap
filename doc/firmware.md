# Фърмуер — бележки и решения

> Документът се допълва с напредването на софтуерната разработка.
> Принцип: **само необходимото** — минимум зависимости и включени модули.

## 1. RGB светодиод WS2812

Вграденият светодиод на ESP32-S3-Zero (GPIO21) изисква драйвер за протокола WS2812
(времена ~0.3 / 0.9 µs, период 1.25 µs) — обикновено управление на GPIO не е достатъчно.
Референтните библиотеки `esp-led-status` и `outputwrite/led_indicator` управляват обикновен светодиод
(GPIO / LEDC) и не поддържат WS2812.

### 1.1 Избор на драйвер

| Вариант | Плюсове | Минуси |
|---|---|---|
| **`espressif/led_strip` (RMT бекенд)** ← *избор* | официален и поддържан от Espressif; проверени времена; малко API | външна зависимост (един компонент, без допълнителни зависимости) |
| Директно RMT + собствен енкодер | нулеви зависимости | собствен код за поддръжка (~80 реда) — дублира `led_strip` |
| SPI бекенд на `led_strip` | — | заема SPI контролер; излишно за 1 светодиод |

Неизползваният код (напр. SPI бекендът на `led_strip`) се отстранява от линкера (`--gc-sections`),
така че в изпълнимия файл влиза само RMT частта.

### 1.2 Минимална конфигурация

`main/idf_component.yml`:

```yaml
dependencies:
  espressif/led_strip: "^3.0.0"
```

Инициализация (1 светодиод, RMT, без DMA):

```c
#include "led_strip.h"

static led_strip_handle_t s_led;

void status_led_init(void)
{
    const led_strip_config_t strip_cfg = {
        .strip_gpio_num = 21,                 // вграден WS2812 на ESP32-S3-Zero
        .max_leds = 1,
        .led_model = LED_MODEL_WS2812,
        .color_component_format = LED_STRIP_COLOR_COMPONENT_FMT_GRB,
    };
    const led_strip_rmt_config_t rmt_cfg = {
        .clk_src = RMT_CLK_SRC_DEFAULT,
        .resolution_hz = 10 * 1000 * 1000,    // 10 MHz → стъпка 0.1 µs
        .mem_block_symbols = 0,               // 0 = минималният размер по подразбиране
        .flags.with_dma = false,              // DMA е излишна за 1 светодиод
    };
    ESP_ERROR_CHECK(led_strip_new_rmt_device(&strip_cfg, &rmt_cfg, &s_led));
    led_strip_clear(s_led);                   // изгасен при старт
}
```

Принципи за минимална употреба:
- Обновяване (`led_strip_set_pixel` + `led_strip_refresh`) **само при промяна** на цвета/състоянието,
  не в постоянен цикъл.
- Шаблоните (мигане, дишане) — с един `esp_timer`, без отделна FreeRTOS задача.
- Яркостта — мащабиране на R/G/B в нашия слой (един коефициент), не в драйвера.

### 1.3 Яркост

- **Решение: 20 %** (коефициент 0.2 върху 0 – 255). Проверено на хардуера: при 25 % синьото вече е доста ярко.
- При нужда се коригира в Kconfig (`CONFIG_SH_LED_BRIGHTNESS`) след монтаж в кутията.
- Предвижда се като настройка (константа / Kconfig, по-късно евентуално и в NVS).

### 1.4 Логика на индикацията

Цветове, шаблони и приоритети: [led-indication.md](led-indication.md).

### 1.5 Ресурси (RMT)

ESP32-S3 има 4 TX и 4 RX RMT канала. Светодиодът заема **1 TX канал**.
Ако за DS18B20 се ползва `espressif/onewire_bus` с RMT бекенд, всяка 1-Wire шина заема 1 TX + 1 RX канал:
2 датчика на отделни GPIO → 2 TX + 2 RX. Общо: **3 TX + 2 RX** — в рамките на наличните.

## 3. HomeKit — прозорец за сдвояване

Проверено в [esp-homekit-sdk](https://github.com/espressif/esp-homekit-sdk) (`components/homekit/esp_hap_core`):

| Елемент | Стойност / API | Бележка |
|---|---|---|
| Продължителност на прозореца | `HAP_PAIRING_MODE_TIMEOUT_IN_MINS = 10` (`src/esp_hap_pair_setup.c`) | по HAP Spec R16; вътрешен таймер `hap_pairing_mode_timer` |
| Таймерът се стартира | при старт без сдвоени контролери; при премахване на последния контролер; при всяко Pair Setup M1 (рестарт); при `hap_pair_setup_re_enable()` | вътрешни извиквания на `hap_start_pairing_mode_timer()` |
| Край на прозореца (изтекло време) | събитие `HAP_EVENT_PAIRING_MODE_TIMED_OUT` | SDK-то спира mDNS обявяването — аксесоарът вече не се вижда за сдвояване |
| Успешно сдвояване | събитие `HAP_EVENT_CTRL_PAIRED` | |
| Опит за сдвояване | `HAP_EVENT_PAIRING_STARTED` / `HAP_EVENT_PAIRING_ABORTED` | |
| Премахнат контролер | `HAP_EVENT_CTRL_UNPAIRED` (+ проверка `hap_get_paired_controller_count() == 0`) | прозорецът се отваря отново |
| Ново отваряне на прозореца | `hap_pair_setup_re_enable()` (публична функция в `hap.h`) | напр. от бутон, без рестарт |
| Брой сдвоени контролери | `hap_get_paired_controller_count()` | |

Няма публична функция „отворен ли е прозорецът“ — състоянието се поддържа във фърмуера от горните събития:

```c
static bool s_pair_window_open;

static void hap_event_handler(hap_event_t event, void *data)
{
    switch (event) {
    case HAP_EVENT_CTRL_PAIRED:
    case HAP_EVENT_PAIRING_MODE_TIMED_OUT:
        s_pair_window_open = false;           // спира дишането
        break;
    case HAP_EVENT_CTRL_UNPAIRED:
        if (hap_get_paired_controller_count() == 0) {
            s_pair_window_open = true;        // SDK-то стартира нов прозорец
        }
        break;
    default:
        break;
    }
    // → преизчисляване на индикацията и енергийния режим
}
// След hap_start(): s_pair_window_open = (hap_get_paired_controller_count() == 0);
// При hap_pair_setup_re_enable():  s_pair_window_open = true;
```

## 4. Енергиен режим на Wi-Fi

- Wi-Fi **не се изключва** — няма отделен режим за настройка с изключване на радиото.
- **Намалена мощност** се прилага само в един случай: прозорецът за сдвояване с HomeKit е изтекъл
  (`HAP_EVENT_PAIRING_MODE_TIMED_OUT`), **без да е имало опит за сдвояване** (не е получено `HAP_EVENT_PAIRING_STARTED`)
  и аксесоарът е останал несдвоен.
  - Мярка: по-ниска максимална мощност на предавателя — `esp_wifi_set_max_tx_power()` (стойността се уточнява на място;
    напр. от ~20 dBm към ~11 – 13 dBm).
  - Нормалната мощност се възстановява при ново отваряне на прозореца (`hap_pair_setup_re_enable()`) и при сдвояване.
- Ако устройството вече е било свързано и **връзката с Wi-Fi се загуби** — енергийният режим на чипа **не се променя**
  (само индикацията преминава в проблясък, а Wi-Fi стекът сам опитва повторно свързване).

## 5. Локално управление — дисплей и бутони

- Бутони: 3 × GPIO с библиотеката `button` (кратко/дълго натискане, автоматично повторение).
- Обновяване на дисплея само при промяна на показваната стойност.
- Дисплей: TM1637, 3 цифри — библиотека [esp_tm1637](https://github.com/AramVartanyan/esp_tm1637); клавиатурата на TM1637 не се използва.

### 5.1 Обновяване на `esp_tm1637` — договорени промени

> Статус: **реализирано в `esp_tm1637` 1.1.0** (компилира се за ESP32, -S3, -C3; тест на хардуер предстои).

| # | Проблем | Решение |
|---|---|---|
| 1 | Изборът на платформа е по `CONFIG_IDF_TARGET_ESP32` / `ESP8266` — за ESP32-S3 (и всички други чипове) се избира клонът за esp-open-rtos и **не се компилира** | Проверка за **`ESP_PLATFORM`** — дефинира се от системата за изграждане на ESP-IDF (и ESP8266_RTOS_SDK) за всички чипове; esp-open-rtos — само ако не е дефиниран |
| 2 | API, премахнато/преместено в ESP-IDF 5.x (`GPIO_PIN_INTR_DISABLE`, `esp32/rom/ets_sys.h` / `ets_delay_us`) | Условия по версия чрез `esp_idf_version.h`: `ESP_IDF_VERSION >= ESP_IDF_VERSION_VAL(5, 0, 0)` → `esp_rom_sys.h` / `esp_rom_delay_us()`, `GPIO_INTR_DISABLE`; за ESP-IDF 4.x и ESP8266 — досегашните извиквания (точната граница на версиите се проверява при реализацията) |
| 3 | Безкрайно изчакване на ACK — при липсващ/повреден дисплей фърмуерът увисва | Изчакване с **ограничение** (напр. до ~100 µs на стъпки от 1 µs); при таймаут — освобождаване на шината (стоп), връщане на грешка и флаг „дисплеят не отговаря“; следващ опит след определено време (напр. 5 s), за да не се губи време при всяко обновяване |
| 4 | Само 4 или 6 цифри | Обща поддръжка за **1 – 6 цифри** (практически 3 и 4); функциите за температура/число — съобразени с броя цифри |
| 5 | CLK/DIO са push-pull изходи, DIO се превключва изход ↔ вход | **Open-drain** режим (`GPIO_MODE_INPUT_OUTPUT_OD`) — виж обяснението по-долу |
| 6 | `malloc` без проверка; няма освобождаване; няма защита при няколко задачи | Проверка за `NULL` (връща `NULL` при неуспех); функция `tm1637_delete()`; правило: дисплеят се обслужва **само от една задача** (без mutex — без допълнителни ресурси) |
| 7 | Клавиатурата на TM1637 не се поддържа | Не е нужна — бутоните са на GPIO |

**Защо open-drain (т. 5):**
- Сега ESP32 *активно* подава и „0“, и „1“ на DIO (push-pull). След 8-ия бит TM1637 дърпа DIO към GND за ACK.
  Ако последният изпратен бит е „1“, за кратко (докато библиотеката превключи DIO на вход) ESP32 подава „1“,
  а TM1637 — „0“: двата изхода се „борят“ (кратко съединение през изходните транзистори).
- При open-drain ESP32 само дърпа линията към GND или я **пуска**; „1“ се осигурява от pull-up резистора (към 3.3 V).
  Така двете страни никога не могат да се борят, няма нужда от превключване изход/вход
  (ESP32 чете нивото на същия извод), а логиката е същата като при I2C.
- Изисква външни pull-up резистори (10 kΩ към 3.3 V — вече предвидени на платката);
  вътрешните (~45 kΩ) са твърде слаби за чисти фронтове.

За уточняване:
- Какво се показва по подразбиране (напр. редуване T_COL / T_TANK, с отличителен знак за кой датчик е).
- Меню и функции на бутоните (настройки на праговете, ръчно включване на помпата, режим Ваканция,
  ново отваряне на прозореца за сдвояване, фабрично нулиране).
- Показване на аварии на дисплея (напр. „E1“, „E2“, грешка на датчик „E3“/„E4“).

### Нулиране с бутона „меню“

| Действие | Време (Kconfig) | Какво се изтрива | Кога става |
|---|---|---|---|
| Нулиране на Wi-Fi | ≥ 5 s, до фабричното (`CONFIG_SH_NET_RESET_HOLD_S`, 3 – 7 s) | само запазената мрежа (`captive_wifi_clear_credentials()` → `esp_wifi_restore()`) | при **пускане** на бутона |
| Фабрично нулиране | 9 s (`CONFIG_SH_FACTORY_RESET_HOLD_S`, 8 – 12 s) | **всичко** в дял `nvs`: сдвояванията с HomeKit, настройките на устройството, Wi-Fi мрежата | още докато бутонът е **задържан** |

- Двата диапазона не се застъпват; компилацията спира, ако фабричното време не е по-дълго.
- След нулирането устройството се рестартира и тръгва в портала `SOLAR-XXXXXX`.
- Фабричното нулиране спира Wi-Fi и изтрива целия дял `nvs` — същото, което прави `hap_reset_to_factory()`
  в esp-homekit-sdk (`hap_keystore_erase_all_data()`). Дялът `factory_nvs` (кодът за сдвояване) е само за четене
  и остава. При добавянето на HomeKit извикването се заменя с `hap_reset_to_factory()` (затваря и сесиите,
  спира mDNS обявяването). Затова всички настройки на устройството се пазят в дял `nvs`.
- Мрежата се пази от Wi-Fi драйвера (`captive-wifi` след 0.2.2: `WIFI_STORAGE_FLASH`, както `app_wifi` и
  `wifi_provisioning` на Espressif). Затова HomeKit вижда същата мрежа (`hap_wifi_is_provisioned()` чете
  `esp_wifi_get_config()`), а `hap_reset_network()` (`esp_wifi_restore()`) я изтрива — с HomeKit нулирането
  на Wi-Fi може да вика `hap_reset_network()` (затваря сесиите, спира mDNS, рестартира).
- HomeKit се стартира при първото свързване (както в mppt-1k): порталът вече е затворен, така уеб сървърът
  на портала и този на HomeKit (порт 80) никога не работят едновременно.
- Логът показва кога е достигнато времето за Wi-Fi („release now …“). Светлинна индикация — с шаблоните на светодиода.

## 6. Макет за разработка — вътрешни pull-up резистори

Докато хардуерът не е завършен, софтуерът се разработва върху **макет** (без окончателните платки).
За макета във фърмуера се **включват вътрешните pull-up резистори** на ESP32-S3 (~45 kΩ към 3.3 V):

| Линия | GPIO | Вътрешен pull-up | Как |
|---|---|---|---|
| DS18B20 колектор | GP1 | ✔ | `onewire_bus` (RMT): `flags.en_pull_up = true` |
| DS18B20 бойлер | GP2 | ✔ | `onewire_bus` (RMT): `flags.en_pull_up = true` |
| TM1637 CLK | GP5 | ✔ | `gpio_config()` — `pull_up_en = GPIO_PULLUP_ENABLE` |
| TM1637 DIO | GP6 | ✔ | `gpio_config()` — `pull_up_en = GPIO_PULLUP_ENABLE` |
| Бутони | GP7 – GP9 | ✔ (и в окончателния вариант) | библиотеката `button` |

- Настройка в Kconfig (напр. `CONFIG_SH_INTERNAL_PULLUPS`, по подразбиране **включена**), за да може след монтиране
  на външните резистори вътрешните да се изключат без промяна на кода.
- Вътрешните резистори са слаби (~45 kΩ) — по-бавни фронтове:
  - **DS18B20:** с кратки кабели обикновено работи; с дългите сонди (95 cm) е възможно нестабилно четене
    (грешки в CRC, „липсващ“ датчик). Ако се случи — един външен 4.7 kΩ на макета решава проблема.
  - **TM1637:** закъснението в библиотеката (сега 3 µs) да е настройваемо, за да може при нужда да се увеличи
    (напр. 10 – 20 µs) — за дисплея скоростта не е важна.
- ⚠️ Ако на макета се ползва **готов модул с TM1637**, той често има собствени pull-up резистори към своето VCC.
  При модул, захранен от 5 V, те трябва да се свалят/преместят към 3.3 V и на макета.
- В окончателните платки остават външните резистори: 4.7 kΩ за датчиците и 10 kΩ за TM1637, към 3.3 V.
