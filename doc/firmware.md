# Фърмуер — бележки и решения

> Документът се допълва с напредването на софтуерната разработка.
> Принцип: **само необходимото** — минимум зависимости и включени модули.

## 1. RGB светодиод WS2812

Вграденият светодиод на ESP32-S3-Zero (GPIO21) изисква драйвер за протокола WS2812
(времена ~0.3 / 0.9 µs, период 1.25 µs) — обикновено управление на GPIO не е достатъчно.
Референтните библиотеки `esp-led-status` и `outputwrite/led_indicator` управляват обикновен светодиод
(GPIO / LEDC) и не поддържат WS2812.

### 1.1 Избор на драйвер

| Вариант | Плюсове | Минуси |
|---|---|---|
| **`espressif/led_strip` (RMT бекенд)** ← *избор* | официален и поддържан от Espressif; проверени времена; малко API | външна зависимост (един компонент, без допълнителни зависимости) |
| Директно RMT + собствен енкодер | нулеви зависимости | собствен код за поддръжка (~80 реда) — дублира `led_strip` |
| SPI бекенд на `led_strip` | — | заема SPI контролер; излишно за 1 светодиод |

Неизползваният код (напр. SPI бекендът на `led_strip`) се отстранява от линкера (`--gc-sections`),
така че в изпълнимия файл влиза само RMT частта.

### 1.2 Минимална конфигурация

`main/idf_component.yml`:

```yaml
dependencies:
  espressif/led_strip: "^3.0.0"
```

Инициализация (1 светодиод, RMT, без DMA):

```c
#include "led_strip.h"

static led_strip_handle_t s_led;

void status_led_init(void)
{
    const led_strip_config_t strip_cfg = {
        .strip_gpio_num = 21,                 // вграден WS2812 на ESP32-S3-Zero
        .max_leds = 1,
        .led_model = LED_MODEL_WS2812,
        .color_component_format = LED_STRIP_COLOR_COMPONENT_FMT_GRB,
    };
    const led_strip_rmt_config_t rmt_cfg = {
        .clk_src = RMT_CLK_SRC_DEFAULT,
        .resolution_hz = 10 * 1000 * 1000,    // 10 MHz → стъпка 0.1 µs
        .mem_block_symbols = 0,               // 0 = минималният размер по подразбиране
        .flags.with_dma = false,              // DMA е излишна за 1 светодиод
    };
    ESP_ERROR_CHECK(led_strip_new_rmt_device(&strip_cfg, &rmt_cfg, &s_led));
    led_strip_clear(s_led);                   // изгасен при старт
}
```

Принципи за минимална употреба:
- Обновяване (`led_strip_set_pixel` + `led_strip_refresh`) **само при промяна** на цвета/състоянието,
  не в постоянен цикъл.
- Шаблоните (мигане, дишане) — с един `esp_timer`, без отделна FreeRTOS задача.
- Яркостта — мащабиране на R/G/B в нашия слой (един коефициент), не в драйвера.

### 1.3 Яркост

- **Решение: 20 %** (коефициент 0.2 върху 0 – 255). Проверено на хардуера: при 25 % синьото вече е доста ярко.
- При нужда се коригира в Kconfig (`CONFIG_SH_LED_BRIGHTNESS`) след монтаж в кутията.
- Предвижда се като настройка (константа / Kconfig, по-късно евентуално и в NVS).

### 1.4 Логика на индикацията

Цветове, шаблони и приоритети: [led-indication.md](led-indication.md). Реализация (стъпка 5):

- `sh_ind` (чист C, тест на компютъра) — една функция `sh_ind_update()`: активните кодове, помпата, колекторът,
  ваканцията, нощното охлаждане, Wi-Fi → (цвят, шаблон). Извиква се от `sh_control` само при промяна на
  входовете.
- Цвят по приоритет: червен (`E1`, `E2`, `E4`, `E5`, `E6`) → оранжев (`Hot`, `Fro`; и докато помпата работи по
  нощното охлаждане — без код, стъпка 10) → лилав (ваканция, стъпка 10) → жълт
  (колектор > 90 °C, помпата спряна; отпада под 88 °C) → зелен (помпата работи — и тестът, защитата от блокиране,
  режимите при повреден датчик) → бял (колектор < 20 °C; отпада над 22 °C) → син. Праговете —
  `CONFIG_SH_LED_COLD_C` (20) и `CONFIG_SH_LED_HOT_C` (90), зоната на връщане 2 K. Без валидна стойност на
  колектора (преди първата или повреден датчик) — нито бял, нито жълт.
- Шаблон: червен — бързо 150 / 150 ms (`E4`, `E5`, и при аварии от двете групи) или двойно (100 вкл., 100 изкл.,
  100 вкл., 1000 тъмно: `E1`, `E2`, `E6`); останалите цветове — постоянно при връзка с Wi-Fi, проблясък 80 ms на
  всеки 2 s без връзка или докато е отворен порталът.
- От стъпка 7 (група E): **обновяване на фърмуера** — бял, мигане 500 / 500 ms, преди всичко останало (и пред
  авариите); **собствена точка за достъп** (`nEt` → `AP`) — огледално на „`CP` без връзка“: свети **постоянно в
  цвета на процеса с кратко угасване 80 ms на всеки 2 s** (шаблон `SH_IND_WINK`); не дишане — то остава само за
  прозореца за сдвояване с HomeKit. Аварийните шаблони и OTA са с предимство.
- `sh_led` — един периодичен `esp_timer` на 10 ms (всички времена са кратни на 10 ms): изчислява дали светодиодът
  свети в момента на шаблона и пише в него **само при промяна**; само таймерът пише в светодиода. Нов шаблон
  започва отначало, нов цвят продължава текущия шаблон. Оранжевият цвят: R 255, G 60, B 0 (преди яркостта) — за
  проверка на хардуера.

### 1.5 Ресурси (RMT)

ESP32-S3 има 4 TX и 4 RX RMT канала. Светодиодът заема **1 TX канал**. DS18B20 не ползват RMT: собственият
драйвер `ds18b20` управлява 1-Wire програмно (прекъсванията са спрени само за един слот, ≤ 70 µs).
Компонентите на Espressif `onewire_bus` + `ds18b20` (RMT) бяха разгледани и отхвърлени: само ESP-IDF 5.x,
без ESP8266, по 1 TX + 1 RX канал на шина.

## 3. HomeKit — прозорец за сдвояване

Проверено в [esp-homekit-sdk](https://github.com/espressif/esp-homekit-sdk) (`components/homekit/esp_hap_core`):

| Елемент | Стойност / API | Бележка |
|---|---|---|
| Продължителност на прозореца | `HAP_PAIRING_MODE_TIMEOUT_IN_MINS = 10` (`src/esp_hap_pair_setup.c`) | по HAP Spec R16; вътрешен таймер `hap_pairing_mode_timer` |
| Таймерът се стартира | при старт без сдвоени контролери; при премахване на последния контролер; при всяко Pair Setup M1 (рестарт); при `hap_pair_setup_re_enable()` | вътрешни извиквания на `hap_start_pairing_mode_timer()` |
| Край на прозореца (изтекло време) | събитие `HAP_EVENT_PAIRING_MODE_TIMED_OUT` | SDK-то спира mDNS обявяването — аксесоарът вече не се вижда за сдвояване |
| Успешно сдвояване | събитие `HAP_EVENT_CTRL_PAIRED` | |
| Опит за сдвояване | `HAP_EVENT_PAIRING_STARTED` / `HAP_EVENT_PAIRING_ABORTED` | |
| Премахнат контролер | `HAP_EVENT_CTRL_UNPAIRED` (+ проверка `hap_get_paired_controller_count() == 0`) | прозорецът се отваря отново |
| Ново отваряне на прозореца | `hap_pair_setup_re_enable()` (публична функция в `hap.h`) | напр. от бутон, без рестарт |
| Брой сдвоени контролери | `hap_get_paired_controller_count()` | |

Няма публична функция „отворен ли е прозорецът“ — състоянието се поддържа във фърмуера от горните събития:

```c
static bool s_pair_window_open;

static void hap_event_handler(hap_event_t event, void *data)
{
    switch (event) {
    case HAP_EVENT_CTRL_PAIRED:
    case HAP_EVENT_PAIRING_MODE_TIMED_OUT:
        s_pair_window_open = false;           // спира дишането
        break;
    case HAP_EVENT_CTRL_UNPAIRED:
        if (hap_get_paired_controller_count() == 0) {
            s_pair_window_open = true;        // SDK-то стартира нов прозорец
        }
        break;
    default:
        break;
    }
    // → преизчисляване на индикацията и енергийния режим
}
// След hap_start(): s_pair_window_open = (hap_get_paired_controller_count() == 0);
// При hap_pair_setup_re_enable():  s_pair_window_open = true;
```

## 4. Енергиен режим на Wi-Fi

- Wi-Fi **не се изключва** — няма отделен режим за настройка с изключване на радиото.
- **Намалена мощност** се прилага само в един случай: прозорецът за сдвояване с HomeKit е изтекъл
  (`HAP_EVENT_PAIRING_MODE_TIMED_OUT`), **без да е имало опит за сдвояване** (не е получено `HAP_EVENT_PAIRING_STARTED`)
  и аксесоарът е останал несдвоен.
  - Мярка: по-ниска максимална мощност на предавателя — `esp_wifi_set_max_tx_power()` (стойността се уточнява на място;
    напр. от ~20 dBm към ~11 – 13 dBm).
  - Нормалната мощност се възстановява при ново отваряне на прозореца (`hap_pair_setup_re_enable()`) и при сдвояване.
- Ако устройството вече е било свързано и **връзката с Wi-Fi се загуби** — енергийният режим на чипа **не се променя**
  (само индикацията преминава в проблясък, а Wi-Fi стекът сам опитва повторно свързване).

## 5. Локално управление — дисплей и бутони

- Бутони: 3 × GPIO с библиотеката `button` (кратко/дълго натискане, автоматично повторение).
- Обновяване на дисплея само при промяна на показваната стойност.
- Дисплей: TM1637, 3 цифри — библиотека [esp_tm1637](https://github.com/AramVartanyan/esp_tm1637); клавиатурата на TM1637 не се използва.

### 5.1 Обновяване на `esp_tm1637` — договорени промени

> Статус: **реализирано в `esp_tm1637` 1.1.0** (компилира се за ESP32, -S3, -C3; тест на хардуер предстои).

| # | Проблем | Решение |
|---|---|---|
| 1 | Изборът на платформа е по `CONFIG_IDF_TARGET_ESP32` / `ESP8266` — за ESP32-S3 (и всички други чипове) се избира клонът за esp-open-rtos и **не се компилира** | Проверка за **`ESP_PLATFORM`** — дефинира се от системата за изграждане на ESP-IDF (и ESP8266_RTOS_SDK) за всички чипове; esp-open-rtos — само ако не е дефиниран |
| 2 | API, премахнато/преместено в ESP-IDF 5.x (`GPIO_PIN_INTR_DISABLE`, `esp32/rom/ets_sys.h` / `ets_delay_us`) | Условия по версия чрез `esp_idf_version.h`: `ESP_IDF_VERSION >= ESP_IDF_VERSION_VAL(5, 0, 0)` → `esp_rom_sys.h` / `esp_rom_delay_us()`, `GPIO_INTR_DISABLE`; за ESP-IDF 4.x и ESP8266 — досегашните извиквания (точната граница на версиите се проверява при реализацията) |
| 3 | Безкрайно изчакване на ACK — при липсващ/повреден дисплей фърмуерът увисва | Изчакване с **ограничение** (напр. до ~100 µs на стъпки от 1 µs); при таймаут — освобождаване на шината (стоп), връщане на грешка и флаг „дисплеят не отговаря“; следващ опит след определено време (напр. 5 s), за да не се губи време при всяко обновяване |
| 4 | Само 4 или 6 цифри | Обща поддръжка за **1 – 6 цифри** (практически 3 и 4); функциите за температура/число — съобразени с броя цифри |
| 5 | CLK/DIO са push-pull изходи, DIO се превключва изход ↔ вход | **Open-drain** режим (`GPIO_MODE_INPUT_OUTPUT_OD`) — виж обяснението по-долу |
| 6 | `malloc` без проверка; няма освобождаване; няма защита при няколко задачи | Проверка за `NULL` (връща `NULL` при неуспех); функция `tm1637_delete()`; правило: дисплеят се обслужва **само от една задача** (без mutex — без допълнителни ресурси) |
| 7 | Клавиатурата на TM1637 не се поддържа | Не е нужна — бутоните са на GPIO |

**Защо open-drain (т. 5):**
- Сега ESP32 *активно* подава и „0“, и „1“ на DIO (push-pull). След 8-ия бит TM1637 дърпа DIO към GND за ACK.
  Ако последният изпратен бит е „1“, за кратко (докато библиотеката превключи DIO на вход) ESP32 подава „1“,
  а TM1637 — „0“: двата изхода се „борят“ (кратко съединение през изходните транзистори).
- При open-drain ESP32 само дърпа линията към GND или я **пуска**; „1“ се осигурява от pull-up резистора (към 3.3 V).
  Така двете страни никога не могат да се борят, няма нужда от превключване изход/вход
  (ESP32 чете нивото на същия извод), а логиката е същата като при I2C.
- Изисква външни pull-up резистори (10 kΩ към 3.3 V — вече предвидени на платката);
  вътрешните (~45 kΩ) са твърде слаби за чисти фронтове.

### Нормален режим на дисплея

Циклично, докато не се влезе в менюто или не тръгне тестът на помпата:

| Стъпка | Показва | Време |
|---|---|---|
| 1 | надпис `Boil` (бойлер) | 1 s |
| 2 | температурата на бойлера | 5 s |
| 3 | надпис `Col` (колектор) | 1 s |
| 4 | температурата на колектора | 5 s |

- „Boil“ на 3 цифри: `b`, `o`, а „i“ (сегмент E) и „l“ (сегменти B, C) са в една цифра. „Col“: `C`, `o`, `l`
  (сегменти E, F). Надписите са зададени като сегменти (XGFEDCBA) в `sh_display.c`.
- Температура: `23.2`, `-9.9`, `150`, `-12` (3 цифри); при неуспешно измерване — последната валидна стойност;
  `---` при **повреден** датчик (5 поредни неуспешни измервания) или преди първата валидна стойност.
- Нова стойност по време на 5-те секунди се показва веднага (проверка на 50 ms); дисплеят се пише само при
  промяна на показаното.
- След стъпка 4 — активните кодове (виж „Аварии и информация“), по 1 s, после надписите, също по 1 s, в този ред:
  `HoL` във ваканция (стъпка 10), ` AP` докато собствената точка за достъп е включена и `FUp` докато потвърдено
  обновяване изчаква или тече (стъпка 7; редът — `sh_menu_label_at()`); после цикълът отначало.
- **`FUp` за 5 s** (стъпка 7) — вместо цикъла, когато автоматичната проверка е намерила по-нова версия; кратко
  „меню“ през това време потвърждава обновяването (виж „Обновяване на фърмуера“).
- При всяко връщане в нормалния екран (от менюто, след теста) цикълът започва от `Boil`.
- Дисплеят се управлява само от задача `sh_display` (`esp_tm1637`: една задача на дисплей); задачата на
  управлението само записва температурите в общото състояние, а менюто (в задачата на бутоните) — какво се
  показва от него (`sh_buttons_menu_view()`).

### Потребителско меню

Позиции в този ред: `SSn`, `HoL`, `tbo`, `C.Lo`, `d.on`, `d.oF`, `tSt`, `nEt`, `End`. Числата са цели, подравнени
вдясно; `SSn`, `HoL` и `nEt` се показват с думи.

| Име | Параметър | Обхват | Стъпка | По подразбиране (Kconfig „Control“) |
|---|---|---|---|---|
| `SSn` | Сезон (стъпка 10) | `Sun` лято / `Cld` зима / `Aut` автоматичен (в този ред, без превъртане) | — | `Aut` |
| `HoL` | Ваканция (стъпка 10) | `oFF` / `on` | — | `oFF` |
| `tbo` | Tmax на бойлера | 30 – 85 °C | 1 | `SH_TANK_MAX_C` (70) |
| `C.Lo` | Минимална температура на колектора — на **текущия сезон** | 10 – 80 °C | 1 | лято `SH_COL_MIN_C` (25), зима `SH_COL_MIN_WINTER_C` (15) |
| `d.on` | Разлика за включване — на текущия сезон | 3 – 20 K, ≥ `d.oF` + 1 | 1 | лято `SH_DIFF_ON_K` (6), зима `SH_DIFF_ON_WINTER_K` (5) |
| `d.oF` | Разлика за изключване — на текущия сезон | 1 – 15 K, ≤ `d.on` − 1 | 1 | лято `SH_DIFF_OFF_K` (4), зима `SH_DIFF_OFF_WINTER_K` (3) |
| `tSt` | Време за тест на помпата | 60 – 900 s | 30 s | `SH_PUMP_TEST_S` (300) |
| `nEt` | Мрежа (стъпка 7) — не е записана настройка | ` CP` / ` AP` („+“ — `AP`, „−“ — `CP`, без превъртане) | — | винаги `CP` при старт |

- **`nEt`** (стъпка 7): стойността, която мига, е текущият режим. Потвърждението се подава към `sh_net` (и при
  същия режим: `CP` включва отново изключено радио, `AP` показва пак кода). След `AP` вместо неподвижната
  стойност се показва **кодът за достъп на две части, по 2 s** (напр. `810`, после `840`; буквите — `A b C d E F`),
  после списъкът на `nEt`; след `CP` — ` CP` за 1 s. **`AP` при връзка с рутера се отказва:** ` CP` неподвижно 1 s,
  после списъкът — нищо не се подава. Натисканията през това време не се вземат предвид.

| Къде | „+“ / „−“ | Кратко „меню“ |
|---|---|---|
| Нормален екран | „+“ — тест на помпата; „−“ — нищо (по време на теста: ± 60 s; по време на обезвъздушаването „+“ не пуска тест) | влиза в списъка, на `SSn` (по време на теста: спира теста; по време на обезвъздушаването: спира го) |
| Списък | следваща / предишна позиция, в кръг (след `End` → `SSn`) | на параметър — стойността мига (0.5 s / 0.5 s); на `End` — нормалният екран |
| Стойност (мига) | ± една стъпка в обхвата, без превъртане; задържане > 1 s → повторение на 200 ms | потвърждава: записва само ако е различна; стойността стои неподвижна 1 s, после списъкът на същата позиция |

- **10 s без натискане** в списъка или на стойност → нормалният екран; непотвърдена стойност не се записва.
- Докато стойността стои неподвижна след потвърждението (1 s), натисканията не се вземат предвид.
- След промяна на стойността миганието започва отначало (новата стойност се вижда веднага).
- Задържане на „+“ / „−“ (повторение) действа само на стойността; в списъка и в нормалния екран задържане над
  1 s не прави нищо (кратко натискане, пуснато след повторение, не се брои — библиотеката `button` подава
  „tap“ и тогава).
- В менюто грешките не се показват. Задържането на „меню“ за нулиранията работи навсякъде (и в менюто).
- Логиката на преходите — `sh_menu` (чист C, тест на компютъра); натисканията идват от `sh_buttons`.

**Запис (`sh_settings_store`):** дял `nvs`, пространство на имената `sh_settings`, ключове `tbo`, `c_lo`,
`d_on`, `d_of`, `t_st` и от стъпка 10 — зимният комплект `c_lo_w`, `d_on_w`, `d_of_w`, сезонът `ssn` (0 лято /
1 зима / 2 автоматичен), ваканцията `hol`, нощното охлаждане над Tmax `nc` (лято) / `nc_w` (зима) (int16) и
текущият сезон `ssn_now` (u8). Четат се при старта; липсваща, извън обхвата или извън стъпката стойност → по
подразбиране; записана двойка с `d.oF` ≥ `d.on` → и двете по подразбиране (всеки сезон — своята двойка). Запис само при промяна. Фабричното
нулиране изтрива `nvs` → стойностите по подразбиране. Управлението чете настройките на всеки цикъл (1 s) —
промяната важи веднага. Минималните времена, защитата на колектора и периодът на измерване остават в Kconfig
(сервизни настройки — по-късно в уеб интерфейса).

### Тест на помпата

- Кратко „+“ в нормалния екран → помпата тръгва **веднага** (без минимален престой) за `tSt`.
- Спират я / не я пускат само забраната при горещ колектор и аварийният таван на бойлера — докато и колекторът е
  горещ (≥ 95 °C, до под 93 °C) или датчикът му е повреден (защита, чийто датчик е повреден, не може да се провери); тестът работи и при повреден датчик. Такава граница **прекратява**
  теста (той не се възобновява, когато тя се отмени); „+“, докато тя е активна, не пуска тест (в лога
  `pump test started` и веднага `pump test ended`).
- „+“ → +60 s (остатъкът най-много 900 s); „−“ → −60 s, само ако остатъкът е над 60 s; „меню“ → край, но не
  по-рано от 1 min след пускането (заявката се изпълнява в края на първата минута).
- Дисплей: `tSt` 3 s, после оставащите секунди; `tSt` отново 1 s на всеки 7 s (6 s време, 1 s `tSt`).
- Край (изтекло време или „меню“): управлението продължава като от спряна помпа с изтекъл минимален престой —
  помпата остава включена, ако режимът би я пуснал (разликата, защитата на колектора, режимите при повреден
  датчик); иначе спира и престоят се брои от края. Минималното време на работа на продължилата помпа също се
  брои от края на теста.
- Тестът прекратява текуща защита от блокиране и текуща проба при повреден датчик.

### Обезвъздушаване (стъпка 10)

- Пуска се от уеб интерфейса („Управление“; `POST /api/air`); **3 цикъла × (работа 5 min + престой)**, престоят =
  10 min × коефициента на вискозитета на топлоносителя (`sh_air_pause_s()` в `sh_installer`: вода 1; пропилен-гликол
  10 % 1.3, 30 % 2.5, 40 % 3.5, 50 % 4.5, 60 % 5.5, линейно между точките) — вода 45 min общо, 60 % гликол 180 min.
- В `sh_pump_ctl`, до теста: по време на работата помпата е включена, по време на престоя — изключена, каквито и да
  са температурите (и Tmax, и зареждането не важат). Спират го и го прекратяват само забраната при горещ колектор
  и аварийният таван при горещ колектор (като теста), „Спри“ в уеб интерфейса и кратко „меню“. Не тръгва, докато върви тестът на
  помпата; докато то върви, „+“ не пуска тест. Краят — както края на теста.
- Дисплей (прието при стъпка 10): `AIr` 3 s при старта, после цикъл от 7 s — фазата 1 s (`run` при работа / `PAu`
  при престой), оставащите минути на цялото обезвъздушаване 5 s, `AIr` 1 s. Уеб интерфейс: цикълът, фазата и
  оставащото време. В лога: начало (с престоя) и край; в историята работата се брои като „друго“.

### Защита от блокиране

- Константи: след **24 h** без работа на помпата (по каквато и да е причина; след рестарт — от старта) помпата
  се завърта за **60 s**, щом колекторът е поне колкото бойлера; ако това не стане до още **12 h** (36 h общо) —
  независимо от температурите. Тестът на помпата се брои за работа.
- Спират я (и я прекратяват) / не я пускат само забраната при горещ колектор и аварийният таван при горещ
  колектор (като теста). Краят — както
  края на теста.
- При повреден датчик сравнението колектор ≥ бойлер не може да се направи → само правилото за 36 h; при двата
  повредени помпата остава спряна (само тестът е разрешен).

### Повреден датчик

**Измерване (`sh_sensors` + `sh_meas`):** неуспешно четене — няма отговор, грешна контролна сума, стойност
извън −55 … +125 °C, скок над 20 K спрямо последната валидна стойност → веднага втори опит с ново измерване;
при скок вторият опит се приема, ако е в рамките на 1 K от скока. Неуспешно измерване → последната валидна
стойност, брояч +1; **5 поредни** → датчикът е повреден (`sh_state`: `col_fault` / `tank_fault`, лог
`... sensor FAULTY`); успешно измерване → брояч 0, повредата отпада (лог `... sensor OK again`).

**Помпата (`sh_pump_ctl`):**

| Повреда | Поведение |
|---|---|
| двата датчика | помпата спряна (тестът — разрешен) |
| бойлер | пускане при колектор ≥ 60 °C (минималният престой важи), спиране под 58 °C (след минималното време); спиране веднага при колектор ≥ 95 °C, ново пускане под 93 °C; Tmax и таванът на бойлера не се ползват; забраната при горещ колектор важи. **Проба:** при спряна помпа и колектор ≥ прага на защитата на колектора (110 °C, таван 115 °C) — работа за минималното време (без престой); в края колекторът < 93 °C → зареждането продължава; иначе спиране и следваща проба не по-рано от 5 h (и след спиране от забраната при горещ колектор по време на пробата) |
| колектор | проба 10 min; покачване на бойлера ≥ 0.5 K → продължава с проверка на всеки 10 min; без покачване → спиране; изчакване 30 / 60 / 120 min след 1 / 2 / ≥ 3 поредни неуспешни проби, след работа с покачване — 30 min; първата проба — веднага щом датчикът е обявен за повреден (минималният престой важи); бойлер ≥ 95 °C (от помпата или от нагревателя) → спиране веднага и проба не по-рано от 5 h; Tmax не се ползва; **нагревател:** при спряна помпа бойлерът е нараснал за последните 10 min поне с прага на признака за нагревател (проба на бойлера всяка минута; прагът — стъпка 12, най-малко 0.5 K) → пробата се отлага |
| възстановяване | нормалната логика продължава с текущото състояние на помпата и времето от последното превключване |

Без валидна стойност от старта, докато датчикът не е обявен за повреден → помпата спряна (`sensor fault`).

### Аварии и информация

`sh_alarm` (чист C, тест на компютъра) — на всеки цикъл на управлението (1 s), след решението за помпата:

| Код | Активен, докато |
|---|---|
| `E1` | датчикът на колектора е повреден |
| `E2` | датчикът на бойлера е повреден |
| `E4` | границата на аварийния таван на бойлера е активна (≥ 95 °C, отпада под 93 °C) и датчикът на бойлера не е повреден |
| `E5` | забраната при горещ колектор е активна (≥ изчислената точка на кипене, отпада под нея − 2 K) и датчикът на колектора не е повреден |
| `E6` | повреда на помпата / няма поток — по-долу |
| `Hot` | помпата работи по защитата на колектора или по пробата при аварийна температура при повреден бойлер (информация) |
| `E8` | обратен термосифон (стъпка 12): обявен след 3 поредни нощи с признака, отпада след 3 поредни нормални нощи — виж „Нагревател, теч от нагревателя, `E8`“ |
| `Fro` | помпата работи по защитата от замръзване (информация; стъпка 6) |

`E4` и `E5` ползват границите на `sh_pump_ctl` (същите, които спират помпата).

**`E6`** ([led-indication.md](led-indication.md), т. 6): проверява се само докато помпата работи непрекъснато по
нормалното управление (разлика, минимално време на работа, защита на колектора) и без повреден датчик. Първите
10 min от пускането се пропускат; от 10-ата минута — проба на двете температури всяка минута, а от 20-ата
минута, всяка минута — сравнение с пробата отпреди 10 min (плъзгащ прозорец, изцяло след първите 10 min):
- **обявяване:** колекторът нараснал ≥ 10 K, бойлерът < 0.5 K и разликата колектор − бойлер ≥ 20 K;
- **отпадане** (при същите проверки): бойлерът нараснал ≥ 0.5 K или разликата под 10 K;
- иначе `E6` стои — и при спряна помпа, тест, защита от блокиране, повреден датчик — до следваща проверка или
  рестарт. Спиране или смяна на причината с ненормална прекъсва работата: при следващото пускане 10 min отначало.
- Праговете — Kconfig „Control“: `SH_E6_TIME_MIN` (10 min — пропуснатото време и прозорецът, 5 – 30),
  `SH_E6_COL_RISE_K` (10), `SH_E6_TANK_RISE_DK` (5 = 0.5 K), `SH_E6_DIFF_K` (20), `SH_E6_CLEAR_DIFF_K` (10;
  проверка при компилиране: под `SH_E6_DIFF_K`). Логиката на помпата не се променя.

Активните кодове се публикуват в `sh_state` (`alarms`, бит на код); всяка поява и отпадане — ред в лога
(`W sh_control: E6 active: collector 75.0 °C, tank 40.0 °C`, `... E6 cleared: ...`).

**Дисплей:** след стандартния цикъл — активните кодове по 1 s, първо авариите по номер (`E8` след `E6`), после
`Hot`, после `Fro` (редът е `sh_alarm_order`; битът на `E8` е след `Fro`, за да не се променят битовете на старите
кодове в историята); после цикълът отначало. `E1` … `E6` подравнени вдясно (` E1`), `Hot` и `Fro` — на трите цифри. В менюто и на екрана на теста —
без кодове. **Светодиод:** виж т. 1.4.

### Данни на монтажника и изчислени граници (стъпка 6)

`sh_installer` (чист C, тест на компютъра) + `sh_installer_store` (дял `nvs`, пространство на имената
`sh_installer`, ключове `fluid`, `glycol`, `press`, `col_max`, `col_type`, `col_area`, `tank_vol`, `heater`, `mount`, int16):

| Данни | Обхват | По подразбиране (Kconfig „Installer data“) |
|---|---|---|
| Топлоносител | вода / пропилен-гликол | `SH_INST_GLYCOL` (изкл. = вода) |
| Пропилен-гликол | 0 – 60 %, стъпка 1 %; при вода — 0 | `SH_INST_GLYCOL_PCT` (0) |
| Минимално налягане (манометър, студена система) | 0.5 – 6.0 bar, стъпка 0.1 (пази се в десети) | `SH_INST_PRESSURE_DBAR` (15 = 1.5 bar) |
| Максимална температура на колектора | 100 – 250 °C, стъпка 1 | `SH_INST_COL_MAX_C` (120) |
| Вид на колектора (стъпка 10) | плосък / вакуумни тръби | `SH_INST_COL_TUBES` (изкл. = плосък) |
| Площ на колектора (стъпка 10) | 0.5 – 20.0 m², стъпка 0.1 (пази се в десети) | `SH_INST_COL_AREA_DM2` (20 = 2.0 m²) |
| Обем на бойлера (стъпка 10) | 50 – 1000 l, стъпка 10 | `SH_INST_TANK_L` (150) |
| Нагревател (стъпка 12) | 0 = няма; 0.5 – 12.0 kW, стъпка 0.5 (пази се в десети) | `SH_INST_HEATER_DKW` (20 = 2.0 kW) |
| Монтаж на датчиците (стъпка 13) | в гилзи / на тръбите (импулсен режим) | `SH_INST_MOUNT_PIPES` (изкл. = в гилзи) |

- Липсваща или извън обхвата стойност → по подразбиране; гликол при вода → 0. Запис само при промяна. Променят се
  от раздела „Сервизни“ на уеб интерфейса (с кода).
- **Точка на кипене:** вода при абсолютно налягане = манометъра + 1.013 bar по уравнението на Антоан (mmHg, °C;
  A = 8.14019, B = 1810.94, C = 244.485; 1 bar = 750.062 mmHg) + добавка от гликола 0 / 20 / 30 / 40 / 50 / 60 % →
  0 / 1 / 2 / 3 / 4 / 6 K (линейно между точките), закръглена **надолу** до 0.1 °C. Вода, 1.5 bar → 127.7 °C;
  9 % PG, 2.2 bar → 136.5 °C.
- **Таван на защитата на колектора** = min(макс. температура на колектора − 5 K, точката на кипене − 10 K);
  настройката `SH_COL_PROTECT_C` (110 °C) се ограничава до него. **Забрана за пускане** = точката на кипене
  (отпада под нея − 2 K).
- **Праг във ваканция** (стъпка 10) = min(75 % от максималната температура на колектора, точката на кипене − 10 K):
  вода, 1.5 bar → 120 °C: 90 °C; 150 °C: 112.5 °C; 180 °C: 117.7 °C.
- **Праг на защитата от замръзване:** вода → 4 °C; пропилен-гликол → точката на замръзване на сместа
  (0 / 10 / … / 60 % → 0 / −3 / −8 / −14 / −22 / −33 / −48 °C, линейно между точките) + 4 K, в границите −40 … +10 °C.
- Константите `SH_PUMP_COL_BOILING` и `SH_PUMP_COL_PROTECT_CAP` са заменени с полета в параметрите на помпата
  (`col_boiling`, `col_protect_cap`); `sh_control` ги взима на всеки цикъл — промяна на данните важи веднага, без
  рестарт. В лога при старта и при всяка промяна: `boiling point (no start) 127.7 °C, collector protection ceiling
  115.0 °C, frost threshold 4.0 °C` и, ако настройката е над тавана, `W … collector protection 110 °C is limited
  to 101.6 °C`.

### Защита от замръзване (стъпка 6)

- В `sh_pump_logic` (нормалният режим), с приоритет: забраната при горещ колектор → аварийният таван → защитата
  на колектора → **защитата от замръзване** → Tmax → разликата. Тестът и защитата от блокиране — както досега.
- **Пускане:** колекторът под прага и бойлерът ≥ 5 °C → веднага (без минимален престой). **Спиране:** колекторът
  ≥ прага + 2 K след минималното време на работа; бойлерът под 5 °C (или изключена защита) → веднага — тогава
  следващите правила решават като за спряна помпа.
- При повреден датчик (режимите на `sh_pump_ctl`) не се проверява.
- Включена / изключена — превключвател в „Настройки“ на уеб интерфейса; пази се в `sh_settings` (ключ `fro`,
  по подразбиране `SH_FROST_PROTECT` = включена).
- Причина `frost protection`; код `Fro` (информация), докато помпата работи по нея; светодиодът — оранжев.

### Нощно охлаждане, ваканция, сезони (стъпка 10)

[operating-modes.md](operating-modes.md) — „Нощно охлаждане (т. 7)“, „Ваканция (т. 8)“, т. 2.1.2; заданието —
[tasks/step10-cooling-vacation-seasons.md](tasks/step10-cooling-vacation-seasons.md). Всичко е в чист C с тест на
компютъра (`test_group_c`); `sh_control` го вика на всеки цикъл преди решението за помпата, в този ред:

**Изгрев и залез (`sh_sun`):**
- **Изгрев:** при спряна помпа колекторът е нараснал с ≥ 2 K спрямо пробата отпреди 10 min (проба всяка минута,
  всичките при спряна помпа), за първи път след полунощ и преди 12:00 (покачване след рестарт следобед не е
  изгрев); без сверен часовник — първото покачване след залеза.
- **Залез:** след като колекторът е бил над бойлера, при спряна помпа пада под него. Ако по-късно пак се качи над
  бойлера и пак падне, за деня важи **последното** падане (то е след дневния пик); ден без колектор над бойлера
  няма залез. От залеза до изгрева (или докато колекторът пак е над бойлера) е „тъмно“.
- **Научени стойности:** при надежден часовник се пазят местните минути на последните 7 засечени изгрева и на
  последните 7 залеза (залезът се взима в полунощ); логиката ползва средното им. Без надежден часовник важи само
  засеченото в същата нощ. Денят ги записва в дневното обобщение (полетата изгрев / залез).

**Сезон (`sh_season`; стойностите — в `sh_settings`):** `Sun` / `Cld` — ръчно, не се превключва. `Aut`: при
надежден часовник в зона с лятно часово време — по него (лятно време → лято); иначе по колектора, само от
текущия сезон към другия, на периоди от 24 h (всеки съдържа една нощ и един ден; броят се от старта): лято → зима —
най-ниската температура на колектора за периода под 5 °C, 3 поредни периода; зима → лято — колекторът над 60 °C,
докато помпата работи без прекъсване над 1 h, 3 поредни периода. Текущият сезон се пази в NVS (`ssn_now`; в
началото лято) и сменя комплекта `C.Lo` / `d.on` / `d.oF` и превключвателя на нощното охлаждане над Tmax. В лога:
`season: winter`.

**Нощно охлаждане (`sh_cool` — кога е разрешено; `sh_pump_logic` — помпата):**

| | |
|---|---|
| Повод а) | бойлерът ≥ Tmax; сезонна настройка (лято вкл., зима изкл.); прозорец **04:00 – 07:00** |
| Повод б) | имало е `E4` след предишната нощ; винаги; прозорец **03:00 – 07:00** |
| Повод в) | ваканция: всяка нощ, от залеза до изгрева; без цел |
| Без надежден часовник | а) / б): от 6 h до 10 h след залеза, засечен в същата нощ; без засечен залез — тази нощ не |
| Сесия | а) / б) започва в прозореца си, докато бойлерът е над целта; една на нощ. Край: бойлерът ≤ целта, краят на прозореца (07:00; без часовник — изгревът, колекторът пак над бойлера или 10 h след залеза), нагревател, повреден датчик |
| Помпата | при активна сесия: тръгва при бойлер − колектор ≥ разликата за включване (след минималния престой), спира при ≤ разликата за изключване (след минималното време на работа); при нова достатъчна разлика тръгва пак. Причина `night cooling` |
| Нагревател | докато помпата работи по охлаждането, бойлерът се е покачил с ≥ 0.5 K над най-ниската си стойност → без охлаждане до следващата нощ; информация в уеб интерфейса |
| Цел | енергия за ясен ден: площта × 2.5 kWh/m² (плосък) или 3.0 kWh/m² (тръби); ΔT = енергия / (обем × 1.163 Wh/(l·K)); цел = 95 °C − ΔT, в границите Tmax − 20 K … Tmax; после научената поправка, в същите граници. 1.8 m² плосък, 120 l → 62.8 °C; по подразбиране (2.0 m², 150 l) → 66.3 °C |
| Самообучение | `E4` в деня след нощ със сесия по а) / б) → поправка −3 K (най-много −20 K); след 7 поредни сутрини без `E4` → +1 K, най-много до изчислената цел |

- **Аварийният таван (уточнено след група C):** спира помпата само докато и колекторът е горещ — `col_hot` в
  `sh_pump_state_t` (≥ 95 °C, отпада под 93 °C), `sh_pump_ceiling_stop()`. С колектор под 93 °C помпата само изважда
  топлина от бойлера: нощното охлаждане, защитата от замръзване, тестът, обезвъздушаването и защитата от блокиране
  работят както обикновено. При повреден датчик на колектора таванът спира теста / обезвъздушаването / защитата от
  блокиране (`emergency()` в `sh_pump_ctl`) и режима на пробите (5 h); при повреден датчик на бойлера — режимът по
  колектора (≥ 95 °C спира). `E4` не се променя (бойлерът ≥ 95 °C, отпада под 93 °C).
- Мястото в `sh_pump_logic` (нормален режим): забрана при горещ колектор → авариен таван → защита на колектора →
  защита от замръзване → **нощно охлаждане** → **ваканция (без зареждане)** → Tmax → разликата. Тестът,
  обезвъздушаването, защитата от блокиране и режимите при повреден датчик (`sh_pump_ctl`) са над него — при
  повреден датчик не се охлажда. Когато сесията свърши при работеща помпа, тя спира по следващите правила: веднага
  във ваканция или при Tmax, иначе след минималното време на работа.
- Индикация: светодиодът **оранжев**, докато помпата работи по охлаждането; на дисплея без код; в историята —
  отделен вид „охлаждане“ (оранжев в графиката, минути в дневното обобщение). В лога: `night cooling started (tank
  above Tmax): target 66.3 °C, until 07:00`, `night cooling ended (target reached): tank 66.2 °C`,
  `night cooling target: learned correction -3 K`, `sunrise detected …`, `sunset detected …`.

**Ваканция:** `HoL` в менюто, превключвател в „Управление“; пази се в NVS (`hol`). Денем — без нормално зареждане
(причина `vacation: no charging`), защитата на колектора работи с прага във ваканция (спира под него − 2 K след
минималното време на работа; кодът `Hot`), аварийният таван и защитата от замръзване важат. Нощем — охлаждане по
повод в): нощта е между научените залез и изгрев (при надежден часовник и двете средни), иначе — от засечения
залез до изгрева. Светодиодът — лилав (оранжев, докато помпата работи); на дисплея след кодовете — `HoL`.
Режимите при повреден датчик не се променят от ваканцията.

**Научени стойности (`sh_learn_store`):** дял `nvs`, пространство `sh_learn` — `sun` (7 изгрева и 7 залеза) и
`cool` (поправката на целта и броят на сутрините без `E4`); записват се при промяна (най-много няколко пъти на
ден). „Нулиране → Научени стойности“ ги изтрива (заедно с проверката на часовата зона).

### Нагревател, теч от нагревателя, `E8` (стъпка 12)

[operating-modes.md](operating-modes.md) — „Нагревател (т. 17)“, „Аварийни съобщения (т. 13)“ (A8 и числата на
признака); заданието — [tasks/step12-heater-leak-e8.md](tasks/step12-heater-leak-e8.md). Всичко е в чист C с тест на
компютъра (`test_group_d`); `sh_control` го вика на всеки цикъл след нощното охлаждане и преди решението за
помпата (входовете — помпата, каквато я е оставил предишният цикъл).

**Признак за работещ нагревател (`sh_heater`, `sh_pump_ctl`):** при спряна помпа бойлерът е нараснал за последните
10 min (проба всяка минута — пробите на `sh_pump_ctl`, които и досега отлагаха пробите при повреден датчик на
колектора) поне с **половината от очакваното покачване за 10 min**: мощност / (обем × 1.163 Wh/(l·K)) / 6 / 2,
закръглено нагоре до 0.1 K, но не по-малко от **0.5 K**; при „0 kW“ — 0.5 K. Примери: 2.0 kW, 150 l → 1.0 K;
3.5 kW, 120 l → 2.1 K; 12 kW, 50 l → 17.2 K. Прагът е `heater_rise` в параметрите на помпата; пробите при повреден
датчик на колектора ползват същия праг.

- **Засечен нагревател:** „0 kW“ и признакът се появи → контролерът приема, че има нагревател (логиката на теча
  важи); информация „Засечен нагревател“ в уеб интерфейса; настройката не се променя. Пази се с научените
  стойности (`sh_learn`, ключ `heater`), нулира се с тях. Лог: `W … heater detected although the installer data
  say 0 kW: tank 45.0 °C`.
- **Минути на нагревателя:** времето с активен признак — в дневното обобщение (полето от група B), в CSV
  (`heater_min`) и в последните 7 дни (колона „Нагр.“).
- Спирането на нощното охлаждане от нагревателя (група C, при работеща помпа) — както досега.

**Гарантирано светлата част на деня** (само при надежден часовник): 09:00 – 16:00 местно време; щом има научени
изгрев и залез (средните на `sh_sun`) — от изгрева + 1 h до залеза − 1 h (началото включено, краят — не); ако научените
не оставят прозорец (изгрев + 1 h не е преди залез − 1 h) — фиксираният.

**Проверки за теч от нагревателя** — само при нагревател (мощност > 0 kW или засечен) и само докато помпата
зарежда по разликата (`difference`, `minimum run time`) в нормален режим; не при защита на колектора / от
замръзване, нощно охлаждане, тест, обезвъздушаване, защита от блокиране, режимите при повреден датчик.

| | |
|---|---|
| С надежден часовник | вътре в светлата част — без проверки; извън нея — след **60 min** непрекъснато зареждане, броено **извън** нея (зареждане от 12:00 → първа проверка в 17:00 при прозорец до 16:00); ако броенето започне привечер (последните 2 h преди научения залез) — след **30 min**; след всяка проверка броенето започва отначало |
| Без надежден часовник | след **30 min** подред, в които колекторът пада (проба всяка минута; покачване започва броенето отначало, общо трябва да е паднал) |
| Проверката | помпата спира веднага за **5 min** (причина `heater leak check`; минималното време на работа не я задържа; защитите действат — ако помпата тръгне по друга причина, проверката се прекратява) |
| Колекторът е паднал < 2 K | помпата тръгва веднага (без минималния престой и минималната температура на колектора), като работеща помпа — докато разликата е над тази за изключване |
| Паднал ≥ 2 K | „течът от нагревателя спрян“ (причина `heater leak stopped`): без пускане по разликата; защитите и нощното охлаждане работят. Край — колекторът се затопли сам с ≥ 2 K за 10 min при спряна помпа, изгревът (`sh_sun`), началото на гарантирано светлата част (надежден часовник — в облачно утро колекторът може да не се затопли с 2 K) или нагревател вече няма |

- Мястото в `sh_pump_logic`: … ваканция → Tmax → **теч от нагревателя** → разликата.
- Лог: `heater leak check: pump off for 300 s, collector 55.0 °C`, `heater leak check: collector fell by 2.3 K ->
  leak of the heater stopped` / `… -> the pump goes on`, `heater leak check given up`, `heater leak stop ended: …`.
- Уеб интерфейс: ред „Теч от нагревателя“ при помпата (проверката с оставащите секунди или последната проверка с
  резултата); информация „Течът от нагревателя е спрян“.

**`E8` — обратен термосифон (`sh_e8`):**

| | |
|---|---|
| Нощ | `sh_sun_night()` — научените средни изгрев / залез при надежден часовник, иначе засеченият залез |
| Признак | нощем, при спряна помпа поне 1 h (проба всяка минута, всичките нощем, при спряна помпа и валидни датчици), за последния час: колекторът е нараснал с ≥ 2 K **и** бойлерът е паднал поне с половината от темпа на термосифона **и** по-бързо от наученото нормално охлаждане (докато го няма — само прагът) **и** \|колектор − бойлер\| е по-малко отпреди час |
| Темп на термосифона | загуба на колектора (плосък 4, вакуумни тръби 1.5 W/m²K) × площта × 40 K / (обем × 1.163); прагът — половината, закръглена нагоре: 1.8 m² плосък, 120 l → 1.1 K/h; 2.0 m², 150 l → 1.0 K/h |
| Нощ с признак / нормална нощ | признакът е изпълнен поне веднъж / поне един час без него; нощ без такъв час (помпата е работила, повреден датчик) не се брои и не прекъсва поредиците. Нощта се преценява в края ѝ |
| Нормално охлаждане | средният темп (K/h) от последните 7 нормални нощи: падането на бойлера минута по минута при спряна помпа, валидни датчици и без признак за нагревател |
| `E8` | след **3 поредни** нощи с признака; отпада след **3 поредни** нормални нощи |

- В NVS (`sh_learn`): `e8rate` (7 темпа), `e8` (двата брояча и `E8`). „Нулиране → Научени стойности“ изтрива
  темповете, но не броячите и `E8`.
- Индикация: дисплеят — `E8` след `E6`; светодиодът — червено двойно мигане; уеб интерфейсът — картата на аварията;
  историята — битът на `E8` (бит 7). Логиката на помпата не се променя. Лог: `W … reverse thermosiphon sign: …`,
  `night judged: 1 night(s) with the reverse thermosiphon sign, 0 normal night(s) in a row`, `W … E8 active: …`.
- В „Система“ → „Научени стойности“: „Нагревател при „0 kW““ (засечен / не) и „Нормално нощно охлаждане“ (K/h).

### Импулсен режим — датчиците на тръбите (стъпка 13)

[operating-modes.md](operating-modes.md) — „Датчици на тръбите — импулсен режим (т. 16)“; заданието —
[tasks/step13-pulse-mode.md](tasks/step13-pulse-mode.md). Всичко е в чист C с тест на компютъра (`test_pulse`):
кога е импулсът — `sh_pulse`; самият импулс, достоверните стойности и решенията по тях — `sh_pump_ctl`.

**Монтаж на датчиците** — данните на монтажника, ключ `mount` (0 в гилзи — по подразбиране, Kconfig
`SH_INST_MOUNT_PIPES`; 1 на тръбите). Смяната важи веднага; достоверните стойности и импулсите започват отначало
(първият импулс — веднага). В режима с гилзи всичко е както досега.

**Достоверни стойности:** тръбите мерят течността едва когато тя тече — **30 s** след пускането на помпата (импулс
или каквато и да е друга работа) и докато работи; тези стойности и кога са взети са „последните достоверни“.
По тях решават всички правила на помпата (разликите, минималната температура на колектора, Tmax, защитите, нощното
охлаждане, режимът при повреден датчик на бойлера), сезонът, нощното охлаждане; по тях са дисплеят, „Температури“,
графиката, историята и цветът на светодиода (бял / жълт). Тръбите при спряна помпа се ползват само вътрешно:
изгрев / залез (`sh_sun`), вратата при замръзване, признакът на нагревателя, `E8`. Повреден датчик изтрива своята
стойност (`---`). При повреден датчик на колектора стойностите са тръбите както са (пробите по 10 min са работа).

**Импулсът (`sh_pump_ctl`):** в нормален режим и при повреден датчик на бойлера спряна помпа без текущи стойности
не тръгва по правилата на режима — тръгва само с импулс, когато `sh_pulse` каже (причина `pulse`), иначе чака
(`waiting for the next pulse`). Импулсът е 30 s (минималното време на работа в този режим); заменят го само тестът
и обезвъздушаването. Краят му — като края на теста, със стойностите, току-що взети: помпата продължава, ако режимът
би я пуснал (разлика ≥ разликата за включване и колектор ≥ минималната му, защита на колектора, замръзване,
нощно охлаждане — колекторът по-студен с ≥ 6 K, при повреден бойлер — колектор ≥ 60 °C), иначе спира до следващия
импулс. Работеща помпа спира по обикновените правила (по стойностите, които следват тръбите).

**Кога (`sh_pulse`), от последната достоверна стойност:**

| | |
|---|---|
| Прозорецът | с надежден часовник 08:00 – 18:00, докато се научат изгревът и залезът, после от научения изгрев до научения залез (началото включено, краят — не); без него — от засечения по тръбите изгрев (≥ 2 K за 10 min при спряна помпа) до засечения залез (тръбата на колектора под тръбата на бойлера — при спряна помпа или по стойностите от импулс след 30 s, `sh_sun_step_flow`) |
| Денем | по колектора: под 50 °C — 30 min; 50 – 80 °C — 10 min; над 80 °C — 3 min |
| Прегрял колектор | достоверен колектор ≥ точката на кипене − 10 K → **без импулси** (предупреждение в уеб интерфейса): с надежден часовник до научения залез, без научен — до 18:00, но не по-рано от 5 h; без надежден часовник — не по-рано от 5 h (от последната такава стойност) |
| Нощем | 3 h |
| Нощно охлаждане / ваканция | 30 min, докато сесия работи или може да започне по последните стойности (прозорецът на повода и бойлерът ≥ Tmax / над целта; ваканцията — цялата нощ) |
| Замръзване | извън прозореца, при включена защита: вратата (праг + 5 K) само започва следенето — тръбата на колектора при спряна помпа падне под нея (импулс веднага) или достоверна стойност е под нея; после до прозореца — по запаса на колектора над прага: ≤ 5 K 30 min, ≤ 10 K 60 min, > 10 K 120 min (вместо 3 h), и импулс веднага, щом тръбата падне с ≥ 3 K под последния импулс; следващата нощ — пак от вратата |
| Без стойност | веднага (старт, смяна на монтажа) |

- **Теч от нагревателя** — не се прилага (`sh_leak` не получава нагревател). **Нагревателят** и **`E8`** — по
  тръбите при спряна помпа, същите признаци и прагове. **`E6`** — само при непрекъсната работа (импулсът не се
  брои; работата след него — от края му). Защитата от блокиране, тестът, обезвъздушаването, засичането на повреден
  датчик — без промяна.
- Графиката / историята: импулсът е „друго“ (сиво).
- Лог: `sensors on the pipes: pulse mode`, `pump ON (pulse)`, `pulse: collector 52.3 °C, tank 41.0 °C`,
  `pump OFF (waiting for the next pulse)`, `W … pulses stopped: collector 118.0 °C, at the boiling point - 10 K`,
  `pulses again after the overheated collector`.
- Уеб интерфейс: „Монтаж на датчиците“ в „Сервизни“ с указанието; под температурите „измерено при импулса в 14:20“
  / „измерено при работа на помпата в …“ / „измерено сега (помпата работи)“; причините „импулс (измерване)“ и
  „изчакване до следващия импулс (след … min)“; режимът „· импулсен“ в „Състояние“; информация „Импулсите са спрени“.

### Уеб интерфейс (стъпка 6 — основа)

Структура, достъп и етапи: [web-interface.md](web-interface.md). Реализация:

- `sh_web` — собствен `esp_http_server` на порт 80. Пуска се при `STA_CONNECTED` и при `AP_STARTED` (стъпка 7:
  в `AP` страницата е на `http://192.168.4.1`), спира при `STA_DISCONNECTED`, `PORTAL_STARTED` и `AP_STOPPED`
  (порталът има свой сървър на същия порт). Пускането и спирането стават в задача `sh_web`; преди `sh_net` да

### Часовник (стъпка 9)

[operating-modes.md](operating-modes.md), т. 3.1. `sh_clock` + правилата в `sh_clock_rules` (чист C, тест на
компютъра) и списъкът със зоните `sh_tz`:

- **SNTP** (`pool.ntp.org`, `esp_netif_sntp`): при всяко свързване с рутера (`STA_CONNECTED`) и после на всеки
  12 h (`CONFIG_LWIP_SNTP_UPDATE_DELAY` = 43 200 000 ms в `sdkconfig.defaults`). Лог: `clock set by SNTP: …`.
- **Часът от браузъра:** страницата го изпраща при всяко отваряне (`POST /api/time`, без кода); приема се само ако
  часовникът не е сверен по SNTP през последните 24 h и е между 2020 и 2099 г.
- **Часова зона:** по подразбиране `UTC`, непотвърдена. Списъкът (81 зони: Европа, Близкият изток, основните
  световни; обединение на списъците от двата варианта на експеримента — общите правила съвпадат) е във фърмуера — името по IANA (както го подава браузърът) и правилото POSIX `TZ` с лятното часово
  време (сверени с tz базата). Страницата предлага зоната на браузъра; монтажникът я потвърждава или избира от
  списъка (с кода). Пази се в NVS (пространство `sh_clock`: `tz` — името, `tz_rule` — правилото, `tz_ok`).
- **Надеждност:** несверен (след старта — до SNTP или браузъра); сверен с **непотвърдена зона** — ненадежден
  (проверката по пика не може да го направи надежден); потвърдена зона — надежден веднага, после по проверката.
- **Проверка по пика** (при потвърдена зона), в полунощ: брои се само пълен ден без повреда на датчика на
  колектора; слънчев — максимумът на колектора ≥ 20 K над минимума му за деня (денонощието от полунощ до полунощ
  — нощният минимум попада в него); пикът — минутата на първия максимум; в прозореца 10:00 – 17:00 (вкл.); 2
  поредни дни извън → ненадежден, 2 поредни в прозореца → отново надежден; облачните дни не прекъсват поредицата.
  Състоянието е научена стойност — в NVS (`sh_clock`, `peak`); нулира се с „Научени стойности“ и с ново
  потвърждаване на зона.

### История (стъпка 9)

[web-interface.md](web-interface.md), т. 4, 4.1. `sh_history` — собствена задача (на 1 s): чете `sh_state` и
`sh_clock` и подава на `sh_day` (чист C); в полунощ записва деня през `sh_hist` (чист C) в дела `history`.

- **Графика за деня (RAM, `sh_day`):** 144 интервала по 10 min — температурите на колектора и бойлера в края на
  интервала (при повреден датчик — няма) и секундите работа на помпата по вид: **зареждане** (разлика, минимално
  време на работа, зареждане при повреден датчик), **защита** (защитата на колектора, замръзването, пробата при аварийна
  температура при повреден бойлер — `Hot`), **друго** (тест, защита от блокиране, пробата при повреден колектор,
  обезвъздушаването), **охлаждане** (нощното охлаждане — стъпка 10; в графиката оранжево като защитата). Със сверен часовник интервалите следват местното време
  и графиката е от полунощ; без часовник — от старта, последните 24 h. „Време на работа днес“ — сборът (със сверен
  часовник — от полунощ или от сверяването).
- **Дневно обобщение (`sh_day`):** само със сверен часовник — макс. / мин. на колектора и бойлера (без
  стойностите при повреден датчик), секундите работа по вид, кодовете през деня, минутата на максимума на
  колектора. В първата стъпка на следващата дата преди 01:00 (нормална полунощ) денят се записва; **пълен** е, ако
  е събран със сверен часовник от полунощ до полунощ без прекъсване, иначе **непълен** (бит в записа). Друга смяна
  на датата (часовникът е сверен на друг ден) изхвърля събраното; същото — скок на местното време с над 1 h в
  рамките на деня (часовникът е сверен наново): денят продължава като непълен. Скок до 1 h (лятно часово време) и
  малките поправки от SNTP не прекъсват деня.
- **Запис (`sh_hist`), 32 B:** формата е в `sh_hist.h` (по т. 4.1 на web-interface.md): дата (ден от 2020 г.),
  4 × температура (0.1 °C, `0x8000` — няма), 3 × минути работа, минути охлаждане (от стъпка 10) и нагревател (от
  стъпка 12 — минутите с активен признак за нагревател),
  авариите (битове), пик (минута, бит 15 — надежден часовник), научени — от стъпка 10: изгревът и залезът, засечени
  този ден (`0xFFFF` — няма), и целта на охлаждането в цели °C (`0xFF` — няма данни в записите отпреди), версия
  1, CRC-8 (0x07) на останалите байтове, резерв (бит 0 — непълен ден).
- **Кръгов буфер:** дял `history` (`data`, `undefined`, `0x350000`, 64 KB) — записите един след друг; преди
  последния запис в сектор се изтрива следващият сектор, така след най-новия винаги има празен запис (по него се
  намира при старта), а най-старият сектор се презаписва: пазят се 1920 – 2047 дни (~5 години). Повреден запис
  (напр. спиране на тока при запис) остава на мястото си и се прескача; място пред главата, което не е празно
  (изгубен бит в свободната част), също се прескача — секторът му **не** се изтрива, за да не се загубят записите
  до него. Дял с непознато съдържание без празен
  запис се изтрива. Без дела (обновяване по OTA със старата таблица) историята е изключена, а в уеб интерфейса е
  сива (`history` липсва в списъка с функциите).
- **CSV:** разделител `;`, десетична точка, заглавен ред на английски (`date;collector_max;…;partial_day;…`),
  датите `YYYY-MM-DD`, часовете `HH:MM`, авариите — кодовете през интервал; „няма данни“ — празно поле.
- **Нулиране** (с кода): „История“ — изтрива дела; „Научени стойности“ — проверката на зоната, научените изгрев
  и залез и поправката на целта на охлаждането (стъпка 10), засеченият нагревател и нормалното нощно охлаждане
  (стъпка 12; броячите на `E8` и самият `E8` остават).
- ⚠️ Таблицата с дялове се сменя само с **пълно прошиване през USB** (`idf.py flash`).

### Мрежа — `nEt`, режим `AP`, име в мрежата (стъпка 7)

[operating-modes.md](operating-modes.md), т. 2.5 („Мрежа — позиция `nEt`“, „Решения за група E“). Библиотеката е
`captive-wifi` **0.4.0**; правилата са в `sh_net_rules` (чист C, тест на компютъра), а задача **`sh_net`** приема
събитията на `captive-wifi` и на `general-ota` и изборите от менюто и уеб интерфейса (една опашка) и изпълнява
каквото правилата поискат. Callback-ът на `captive-wifi` само подава събитието в опашката (той се вика от задачите
на библиотеката; `captive_wifi_start()` се вика от задачата на приложението).

| Режим | Какво става |
|---|---|
| `CP`, има запазена мрежа | `captive_wifi_start()`: рутерът, SNTP, уеб интерфейсът, mDNS — както досега; радиото не се изключва |
| `CP`, няма запазена мрежа | порталът за настройка; след **15 min** без клиент `captive-wifi` го затваря и изключва радиото (`CONFIG_CAPTIVE_WIFI_PORTAL_IDLE_MIN=15`, събитие `PORTAL_TIMEOUT`) — до рестарт или избор от `nEt` (`CP` → порталът отново, `AP` → точката за достъп) |
| `AP` | `captive_wifi_start_ap(900)` (`CONFIG_CAPTIVE_WIFI_AP_ONLY=y`): отворената мрежа `Solar-xxxxxx` без изскачащ прозорец, уеб интерфейсът на `http://192.168.4.1`, часът — от браузъра; 15 min без клиент (от пускането и от последното откачане) → `CP`: с мрежа — към рутера, без мрежа — радиото се изключва |

- Режимът **не се пази**: при всеки старт е `CP`. Избира се **само от менюто** (`nEt`); уеб интерфейсът само го
  показва („Система“ → „Мрежа“ → „Режим“) — страница през рутера означава, че контролерът е свързан с него.
- **`AP` е позволен само когато контролерът не е свързан с рутера** — няма запазена мрежа (порталът), рутерът не
  отговаря (опитва се безуспешно) или радиото е спряно. При връзка изборът се отказва: дисплеят показва ` CP`
  неподвижно 1 s и се връща в списъка (без кода); отказват го и `sh_menu`, и `sh_net_rules` (в лога: `nEt: AP is
  refused — connected to the router`).
- **Нулирането на Wi-Fi** (бутонът 5 s и уеб интерфейсът) и фабричното нулиране са винаги позволени (и в `AP`); след
  тях — порталът. Радиото спира само без запазена мрежа (порталът или `AP` след 15 min без клиент); при връзка с
  рутера — никога.
- **Времето в `AP`** се брои на две места с еднакви правила: в `sh_net_rules` (тестваното; `SH_NET_AP_IDLE_S` =
  900 s, клиентите — по `AP_CLIENT_CONNECTED` / `_DISCONNECTED`) и в `captive-wifi` (`AP_TIMEOUT`). Което изтече
  първо, връща към `CP`; другото после не прави нищо.
- **Избор на `AP` по време на обновяване** (докато се записва новата версия, до рестарта) се отлага до края му; ако
  обновяването не успее, `AP` тръгва тогава. Избор на `CP` междувременно отменя отложения `AP`.
- **Индикация** докато `AP` е включен: светодиодът свети постоянно в цвета на процеса с угасване 80 ms на всеки
  2 s; дисплеят — ` AP` за 1 s след кодовете (виж „Нормален режим на дисплея“). В общото състояние — `net_ap`.
- **Името и MAC адресът** — всичко е от **основния MAC** (`ESP_MAC_BASE`), напр. `e8:f6:0a:81:08:40`:

  | | | Откъде |
  |---|---|---|
  | Име | `Solar-810840` | `captive_wifi_ap_ssid()` — `Solar` (`CONFIG_CAPTIVE_WIFI_AP_SSID_PREFIX`) и последните 6 знака от основния MAC с малки букви; **един и същ текст** за мрежата на портала / `AP`, името в рутера (DHCP) и mDNS (`Solar-810840.local`) |
  | Код за „Сервизни“ / „Система“ | `810840` | последните 6 знака от името (`sh_net_code()`); приема се с малки и главни букви; на дисплея — `810` → `840` (буквите `A b C d E F`) |
  | Сериен номер („Фърмуер“) | `E8F60A810840` | основният MAC с главни букви (`sh_net_serial()`) |

  Името се задава на станцията след `captive_wifi_init()` (`esp_netif_set_hostname()`, преди свързването);
  настройката `CONFIG_SH_HOSTNAME` отпада. При старта `sh_net` проверява, че името следва основния MAC
  (`sh_net_name_ok()`; иначе грешка в лога — подмодулът `captive-wifi` е по-стар). **mDNS** (`espressif/mdns`,
  управляван компонент): `Solar-xxxxxx.local` и услуга `_http._tcp` на порт 80 — само на станцията
  (`CONFIG_MDNS_PREDEF_NETIF_AP=n`), т.е. в `CP` при връзка с рутера; в `AP` адресът е `192.168.4.1`. Името е и в
  лога при старта, в уеб интерфейса („Система“ → „Име в мрежата“) и в името на CSV файла.
- ⚠️ Новите стойности в `sdkconfig.defaults` (`CAPTIVE_WIFI_AP_ONLY`, `CAPTIVE_WIFI_PORTAL_IDLE_MIN`,
  `GENERAL_OTA_URL`) важат само за нов `sdkconfig`: съществуващият файл се
  изтрива преди компилацията (`rm sdkconfig`), иначе `nEt` → `AP` не прави нищо (грешка в лога, режимът остава `CP`).

### Обновяване на фърмуера — OTA, `FUp` (стъпка 7)

[web-interface.md](web-interface.md), т. 5. Библиотеката е `general-ota`; правилата са в `sh_ota` (чист C, тест
на компютъра), изпълнява ги задачата `sh_net`. Източник: `CONFIG_GENERAL_OTA_URL` =
`https://raw.githubusercontent.com/AramVartanyan/otafw/master/solheat1.bin`; инсталира се само строго по-нова
версия от `CONFIG_APP_PROJECT_VER`.

| Стъпка | Правило |
|---|---|
| Автоматична проверка | **веднъж след старта**: 1 min след старта, ако тогава контролерът е в `CP` и е свързан с рутера; ако връзката дойде по-късно (рутерът тръгва по-бавно след спиране на тока, връщане от `AP`) — **1 min след нея** (ако връзката се изгуби преди това, минутата започва от следващото свързване). Повторно губене и връщане на връзката не прави нова проверка; в `AP` проверка няма; неуспехът — само в лога (и тя се брои за направена) |
| Има по-нова версия | на дисплея **`FUp` за 5 s**; кратко „меню“ през това време потвърждава; без потвърждение не се инсталира нищо (версията остава видима в уеб интерфейса) |
| От уеб интерфейса | „Проверка за обновяване“ → „Версията е актуална“ / „Налична е по-нова версия x.y.z“ с бутон „Обнови“ (без `FUp` на дисплея); неуспешна проверка — „Няма връзка със сървъра за обновяване“; в `AP` редът е сив: „Няма интернет (собствена точка за достъп)“ |
| Кога тръгва | веднага, ако контролерът е свързан с рутера, **помпата не работи**, няма **активна защита** (`Hot`, `Fro`, `E4`, `E5`) и не върви обезвъздушаване; иначе **изчаква** и тръгва само, щом може |
| Докато изчаква или тече | `FUp` сред надписите на нормалния екран (1 s след кодовете); в уеб интерфейса — състоянието в „Система“ и карта в „Състояние“ |
| Докато тече | светодиодът — бял, мигане 500 ms; логиката на помпата продължава; уеб интерфейсът показва напредъка и „не изключвайте захранването“ |
| Успех | `general-ota` рестартира (след 3 s) в новата версия |
| Неуспех (изтегляне или проверка на образа) | остава работещата версия; нова проверка — от уеб интерфейса или след рестарт |

- **При неуспех — старата версия:** новата версия се пише в другия OTA дял и се превключва към нея само ако е
  изтеглена цяла и образът е проверен (`esp_https_ota_finish()`); иначе работещата остава. Връщане в bootloader-а
  (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`) **не се включва** (както в mppt-1k): пази само първите минути след
  обновяването, а HomeKit не допуска връщане към по-стара версия. Bootloader-ът не се променя.
- В общото състояние: `ota_running` (записва се новата версия — за светодиода), `fup_offer` (`FUp` се предлага),
  `fup` (потвърдено обновяване изчаква или тече).
- Лог (`sh_net`): всяка смяна на състоянието — `firmware 0.1.0: newer version available — 0.2.0`, `… confirmed,
  waiting for the pump`, `… updating`, `… written, restarting`, `… failed, the running version stays`.

### Нулиране с бутона „меню“

| Действие | Време (Kconfig) | Какво се изтрива | Кога става |
|---|---|---|---|
| Нулиране на Wi-Fi | ≥ 5 s, до фабричното (`CONFIG_SH_NET_RESET_HOLD_S`, 3 – 7 s) | само запазената мрежа (`captive_wifi_clear_credentials()` → `esp_wifi_restore()`) | при **пускане** на бутона |
| Фабрично нулиране | 9 s (`CONFIG_SH_FACTORY_RESET_HOLD_S`, 8 – 12 s) | **всичко** в дял `nvs`: сдвояванията с HomeKit, настройките на устройството, Wi-Fi мрежата | още докато бутонът е **задържан** |

- Двата диапазона не се застъпват; компилацията спира, ако фабричното време не е по-дълго.
- След нулирането устройството се рестартира и тръгва в портала `Solar-xxxxxx`.
- Фабричното нулиране спира Wi-Fi и изтрива целия дял `nvs` — същото, което прави `hap_reset_to_factory()`
  в esp-homekit-sdk (`hap_keystore_erase_all_data()`). Дялът `factory_nvs` (кодът за сдвояване) е само за четене
  и остава. При добавянето на HomeKit извикването се заменя с `hap_reset_to_factory()` (затваря и сесиите,
  спира mDNS обявяването). Затова всички настройки на устройството се пазят в дял `nvs`.
- Мрежата се пази от Wi-Fi драйвера (`captive-wifi` след 0.2.2: `WIFI_STORAGE_FLASH`, както `app_wifi` и
  `wifi_provisioning` на Espressif). Затова HomeKit вижда същата мрежа (`hap_wifi_is_provisioned()` чете
  `esp_wifi_get_config()`), а `hap_reset_network()` (`esp_wifi_restore()`) я изтрива — с HomeKit нулирането
  на Wi-Fi може да вика `hap_reset_network()` (затваря сесиите, спира mDNS, рестартира).
- HomeKit се стартира при първото свързване (както в mppt-1k): порталът вече е затворен, така уеб сървърът
  на портала и този на HomeKit (порт 80) никога не работят едновременно.
- Логът показва кога е достигнато времето за Wi-Fi („release now …“). Светлинна индикация — с шаблоните на светодиода.

## 6. Макет за разработка — вътрешни pull-up резистори

Докато хардуерът не е завършен, софтуерът се разработва върху **макет** (без окончателните платки).
За макета във фърмуера се **включват вътрешните pull-up резистори** на ESP32-S3 (~45 kΩ към 3.3 V):

| Линия | GPIO | Вътрешен pull-up | Как |
|---|---|---|---|
| DS18B20 колектор | GP1 | ✔ | `ds18b20`: `CONFIG_ONEWIRE_INTERNAL_PULLUP` (избира се от `CONFIG_SH_INTERNAL_PULLUPS`) |
| DS18B20 бойлер | GP2 | ✔ | `ds18b20`: `CONFIG_ONEWIRE_INTERNAL_PULLUP` (избира се от `CONFIG_SH_INTERNAL_PULLUPS`) |
| TM1637 CLK | GP5 | ✔ | `gpio_config()` — `pull_up_en = GPIO_PULLUP_ENABLE` |
| TM1637 DIO | GP6 | ✔ | `gpio_config()` — `pull_up_en = GPIO_PULLUP_ENABLE` |
| Бутони | GP7 – GP9 | ✔ (и в окончателния вариант) | библиотеката `button` |

- Настройка в Kconfig (напр. `CONFIG_SH_INTERNAL_PULLUPS`, по подразбиране **включена**), за да може след монтиране
  на външните резистори вътрешните да се изключат без промяна на кода.
- Вътрешните резистори са слаби (~45 kΩ) — по-бавни фронтове:
  - **DS18B20:** с кратки кабели обикновено работи; с дългите сонди (95 cm) е възможно нестабилно четене
    (грешки в CRC, „липсващ“ датчик). Ако се случи — един външен 4.7 kΩ на макета решава проблема.
  - **TM1637:** закъснението в библиотеката (сега 3 µs) да е настройваемо, за да може при нужда да се увеличи
    (напр. 10 – 20 µs) — за дисплея скоростта не е важна.
- ⚠️ Ако на макета се ползва **готов модул с TM1637**, той често има собствени pull-up резистори към своето VCC.
  При модул, захранен от 5 V, те трябва да се свалят/преместят към 3.3 V и на макета.
- В окончателните платки остават външните резистори: 4.7 kΩ за датчиците и 10 kΩ за TM1637, към 3.3 V.
